### 发现 11：Runner.Steer 在 Stop 与 end 之间的小窗口可成功写入但 Steer 被丢弃

- 位置：kernel/runner/steer.go:11–23、kernel/runner/run.go:223–238
- 维度：正确性（并发竞争——事件顺序）
- 严重度：P3
- 归类：B 空白（文档未规定 Stop 与 Steer 的原子性保证）
- 问题描述与证据：`Steer` 先通过 `r.current()` 取到 `liveRun`（释放 `r.mu`），再获取 `current.mu` 检查 `steeringClosed`。在两次加锁之间，`stop()` 可能已设置 `stopped=true` 并 cancel context，但尚未调用 `end()` 设置 `steeringClosed=true`。此窗口内 `Steer` 会成功追加到 `steers` 切片，但 Run 因 context 取消即将退出，不会在 checkpoint 中取走这条 Steer。Steer 被静默丢弃。
  失败场景：用户在 CLI/API 层先调 Stop 再立刻调 Steer，且两者恰好在上述窗口交错。UI 层不可达此窗口（Stop 返回后 UI 等 run-ended 再开放输入），故实际风险极低。
- 建议与代价：可在 `stop()` 中同时设置 `steeringClosed=true` 和 `followUpsClosed=true`，使 Steer/FollowUp 立刻返回错误。改动 2 行，无波及。

### 发现 17：events.Registry 无 listener panic 保护

- 位置：kernel/events/registry.go:72–78
- 维度：正确性（错误路径——listener panic 会崩溃整个进程）
- 严重度：P1
- 归类：B 空白（文档未规定 listener 必须 recover，但生产代码不应因订阅者 panic 而崩溃）
- 问题描述与证据：`Publish` 直接调用 `item.call(ctx, event)`，无 `recover`。如果任何 `Subscribe` 的 handler panic（比如 nil 指针、类型断言失败），整个进程崩溃。当前内置的 Chat 和 Dock listener 都很安全，但第三方插件通过 events.Subscribe 注册的 handler 没有此保证。
  失败场景：一个观测插件在 handler 中对 RunEvent 做了错误的类型断言并 panic → 进程崩溃 → 所有会话中断。
- 建议与代价：在 `Publish` 的 for 循环中为每个 `item.call` 加 `recover`，将 panic 转为 error 并收集到 errs 中。改动约 8 行，不影响正常路径。
