### 发现 1：selectModel 阻止首次发送后更改模型与思考档位

- 位置：`plugins/products/chat/handler.go:572-579`
- 维度：正确性 / 维度 4
- 严重度：P0
- 归类：A 违规

- 问题描述与证据：

  `selectModel` 在 Model 和 ReasoningEffort 均已设置时直接返回 nil，忽略请求中的任何变更：

  ```go
  func (h *PageHandler) selectModel(sessionID, model, effort string) error {
      setup, err := h.settings.For(sessionID)
      if err != nil {
          return err
      }
      if setup.Model != "" && setup.ReasoningEffort != "" {
          return nil  // ← 已设置，不做任何变更
      }
      // ...
  }
  ```

  失败场景：用户首次发送选择模型 A + effort "high"，成功。之后在 UI 切换为模型 B + effort "off"，再次发送——`selectModel` 直接 return nil，后续 Run 仍使用模型 A + "high"。用户以为已切换，实际未切换。

  违反设计书 §10：「前端改模型、思考档位、工作区都 `sessionSettings.Put`」——明确说这三个都应可改。
  违反 STATUS.md 声称：「换模型会清空档位」——实际无此功能。

- 建议与代价：去掉 `if setup.Model != "" && setup.ReasoningEffort != ""` 提前返回；改为始终接受请求中的 model/effort 并 Put。换模型时清空档位的逻辑在前端 JS（filterEfforts 已部分实现）配合后端 Put 即可。波及面：handler.go 一处函数 + 前端 chat.js 的 filterEfforts 行为确认。

### 发现 8：renderComponent 使用 context.Background()

- 位置：`plugins/products/chat/handler.go:235`
- 维度：2（职责清晰）
- 严重度：P2
- 归类：B 空白

- 问题描述与证据：

  ```go
  func renderComponent(component templ.Component) (string, error) {
      var output bytes.Buffer
      err := component.Render(context.Background(), &output)
      // ...
  }
  ```

  此函数在 SSE 写入路径 (`writeDockEvent`) 中调用，丢弃了请求 Context。若客户端断开，templ 渲染仍会执行到完成。当前 Dock 内容简单，影响极小；但若未来面板内容变重或依赖 Context（超时、追踪），此处会成为不可取消的长阻塞。

- 建议与代价：给 `renderComponent` 加 `ctx context.Context` 参数，从 `writeDockEvent` 传入 `r.Context()`。波及面：一处函数签名 + 两处调用点。

### 发现 9：Dock/Panel/MessageAction 登记处缺少互斥保护

- 位置：`plugins/products/chat/docks.go`、`panels.go`、`message_actions.go`
- 维度：3（风格统一）
- 严重度：P2
- 归类：B 空白

- 问题描述与证据：

  `DockRegistry`、`PanelRegistry`、`messageActionRegistry` 内部用裸 `map`，无 `sync.RWMutex`。对比同层级的 `tools.Registry`、`loops.Registry`、`skills.Registry` 均有 `sync.RWMutex` 保护。

  当前安全是因为所有 Register 调用都在启动阶段（单线程），HTTP 服务尚未开始。但如果有人误在运行时调用 Register（例如未来动态注册 Dock），会触发 Go map 并发读写 panic，且无编译期或运行时防护。

- 建议与代价：加 `sync.RWMutex`，与 kernel 登记处风格统一。波及面：每个登记处加 mu 字段 + Lock/RLock 包裹，约 20 行。

### 发现 13：selectModel 不校验请求的 model/effort 是否可用

- 位置：`plugins/products/chat/handler.go:572-596`
- 维度：正确性
- 严重度：P1
- 归类：A 违规

- 问题描述与证据：

  当 `setup.Model` 和 `setup.ReasoningEffort` 均为空时（首次发送），`selectModel` 校验请求中的 model/effort 是否在可用列表中。但当两者均已设置时（发现 1 的路径），函数直接 return nil——即使请求中的 model/effort 不合法（如被管理员删除的模型），也通过校验。

## 总评

1. **架构（维度 1）**：分层清晰，import 方向无违规，Host 服务表形态一致，内核不依赖表面和插件。
2. **职责（维度 2）**：内核各包职责分明；Chat handler 是唯一显著的大块，建议拆分。
3. **风格（维度 3）**：整体高度统一（命名、注释、错误处理）；局部不一致：chat 注册处缺 mutex、两处类型缺标注、一处缩进混 tab。
4. **文档一致（维度 4）**：STATUS.md 两处声称与代码不符（模型切换、阶段标签）；这是本次审查最值得注意的发现。
5. **闭门造车（维度 5）**：未发现；项目已使用 goai、jsonschema、templ、htmx 等生态轮子，且设计书 §18 明确列出不抄项。
6. **过度设计（维度 6）**：未发现显著过度设计；接口数量克制，无预建空插槽。
7. **测试缺口（维度 7）**：四个工具插件、chat handler、chat reducer 均无测试，是承重墙缺口。
8. **演进阻力（维度 8）**：handler.go 单体会随新端点膨胀；pageData 全量读设置在会话量大时变慢；selectModel 锁定模型后无法切换会阻塞后续模型管理功能。

**置顶确认**：发现 1（selectModel 阻止模型切换）是正确性问题，有具体失败场景，排在最前。
