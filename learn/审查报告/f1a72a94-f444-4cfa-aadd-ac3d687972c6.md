### 发现 1：Runner 关闭与开局之间存在竞态，Close 之后仍会跑完一整轮 Run

- 位置：`kernel/runner/run.go:100-113`（Start）、`kernel/runner/run.go:130-137`（runOne 开头）、`kernel/runner/steer.go:106-111`（openSteering）、`kernel/runner/steer.go:161-169`（stop）、`kernel/runner/run.go:311-323`（close）
- 维度：正确性
- 严重度：P0（正确性）
- 归类：A 违规（违反 `STATUS.md:36`「`Runner.Close` 会取消并等待仍在运行的 Run」的声称；亦不符合设计书 §11 对 Runner 外壳职责的描述）
- 问题描述与证据：`liveRun.cancel` 在 `runOne` 的 `setCancel` 之后才非空，而 `stop()` 只能取消 `current.cancel` 并置 `stopped=true`；`runOne` 开头的 `openSteering()` 又把 `stopped` 重置为 `false`（这个重置是为「Stop 不清空 FollowUp、下一轮照常开」设计的）。于是存在这样的确认失败场景：
  1. goroutine A：`Runner.Start` → `begin()` 成功（占住 live、`wg.Add(1)`），`runOne` 尚未执行到 `setCancel`；
  2. goroutine B：`Host.Close` → `runner.close()` → `closeStarted=true`，对 current 调 `stop()`——此刻 `current.cancel == nil`，只能留下 `stopped=true`；随后 `wg.Wait()` 阻塞；
  3. goroutine A 的 `runOne` 开始：`openSteering()` 把 `stopped` 清回 `false`，随后的 `setCancel` 看到 `stopped == false`，不取消；
  4. 结果：整轮 Run（LLM 调用、账本写入、事件发布）在 Close 宣告开始后照常执行，`close()` 的等待被拖到这一轮自然结束。`isClosing()` 只在 `run()` 里 `runOne` 返回之后才检查，救不了第一轮。
  同根问题：用户发送后立刻点「停止」，若 `Stop` 落在 `setCancel` 之前，同样被 `openSteering` 抹掉，本轮不取消且界面已显示过「已停止」路径的副作用。
  现有 `TestCloseCancelsAndWaitsForManagedRun` 测不到它：测试里 loop 先 `close(ready)`（已进入 `loop.Run`，cancel 已设置），close 才发生。
- 建议与代价：`runOne` 开头（或 `run` 每轮进入前）加 `if r.isClosing() { return err }`，一行即可封死 Close 竞态。Stop 竞态涉及「Stop 后 FollowUp 是否开新一轮」的语义取舍（现行为有代码注释与测试背书），建议分开处理：close 检查与 `stopped` 重置解耦，例如 `openSteering` 不再碰 `stopped`，FollowUp 新一轮的「可取消重置」用单独标记表达。改动全部在 runner 包内，补一条「Start 后立即 Close」的测试即可锁住。

## 总评（每维度一句）

1. **架构**：分层与依赖方向完全干净——kernel 不 import plugins/surface、web 不认识填充者、定义者/提供者/消费者三向不交叉，服务表形状与设计书 §1 逐键对应。
2. **职责**：A 整份服务 / B 登记处形态用得对，登记处校验齐整；唯一含混是 Chat 的路由知识写了两份（发现 6）。
3. **风格**：词汇表（登记处/插槽/活对象/数据/契约）在类型注释里贯彻得很好；最大的不统一是 err 两行规则有名无实（发现 3）与 nil 防护忽有忽无（发现 11）。
4. **文档符合**：代码→文档方向未发现实质违规；文档→代码方向存在整块未实现的配置面（发现 4）与过期文案（发现 8）；STATUS 声称基本属实。
5. **闭门造车**：未发现造轮子造成实际伤害——SSE 帧写出、事件枢纽、按类型事件登记处都是小而有测试的实现；手写的 Windows COM 选择器是唯一高风险自制件（存疑 1）。
6. **过度设计**：整体克制，没有空目录、没有 util/common；仅 `Choices()`（发现 9）与 Media 契约属预建，代价都小。
7. **测试缺口**：Go 侧覆盖扎实（runner 并发与取消、chat 端到端、事件枢纽、SSE 多行帧、截断、schema 校验都有针对性测试）；最大缺口是前端 reducer 零测试（发现 2）与非 darwin 构建件零验证（存疑 1）。
8. **演进阻力**：分叉 / 轨迹页接入时会撞墙的点按优先级：RunEvent→timelineEvent→chat.js 三处同步（发现 7）、paint() 全量重绘（发现 12）、Branch 光标不持久化（C 类，落地分叉 UI 时需补持久化设计）、以及发现 1 的 Runner 竞态（子任务 Spawn 建立在 Runner 生命周期正确性之上）。
