### 发现 1：首次选模型后无法再换模型和思考档位

- 位置：`plugins/products/chat/handler.go:572-596`
- 维度：正确性
- 严重度：P0
- 归类：A 违规

**问题描述与证据**：

`selectModel` 在 Model 和 ReasoningEffort 都已设值时直接返回 nil，完全忽略表单提交的新值：

```go
func (h *PageHandler) selectModel(sessionID, model, effort string) error {
    setup, err := h.settings.For(sessionID)
    // ...
    if setup.Model != "" && setup.ReasoningEffort != "" {
        return nil // ← 已有值就跳过，不更新
    }
    // ...后续逻辑只在空值时执行
}
```

前端 `chat.js` 每次提交都带上 model 和 effort 表单值，用户在 UI 改选后提交，但后端一律忽略。

STATUS.md 明文声称「换模型会清空档位」，设计书 §10 说「前端改模型、思考档位、工作区都 `sessionSettings.Put`」。代码违反了两份文档。

**建议与代价**：去掉 `if setup.Model != "" && setup.ReasoningEffort != "" { return nil }` 这个提前返回，改为始终用表单值更新 settings（校验有效性后 Put）。改动限于 `selectModel` 一个函数，不影响其他包。

### 发现 3：Chat 三个插槽登记处缺少并发保护，与 kernel 同类不一致

- 位置：`plugins/products/chat/panels.go:10-12`、`plugins/products/chat/docks.go:12-14`、`plugins/products/chat/message_actions.go:9-11`
- 维度：3（风格不统一）
- 严重度：P2
- 归类：B 空白

**问题描述与证据**：

kernel 下的所有登记处（`loops.Registry`、`tools.Registry`、`skills.Registry`、`events.Registry`）都用 `sync.RWMutex` 保护 map。Chat 的 `PanelRegistry`、`DockRegistry`、`messageActionRegistry` 都用裸 `map[string]T`，无锁。

当前不会出错（Start 顺序执行、写完再读），但与 kernel 风格不一致；若未来允许运行时动态登记（如 MCP 工具上线），将产生数据竞争。

**建议与代价**：给三个 Registry 加 `sync.RWMutex`，读用 RLock、写用 Lock。改动限于三个文件，对外接口不变。

### 发现 9：React Loop 未处理增量工具调用流

- 位置：`plugins/loops/react/react.go:123-133`
- 维度：演进阻力
- 严重度：P2
- 归类：B 空白

**问题描述与证据**：

收到 `ChunkToolCall` 时，代码直接 `append(calls, call)` 并 `append(message.Blocks, ...)`。若 goai 某家 Provider 以多个 chunk 流式发送同一个工具调用（先 ID 后 args），当前代码会为同一调用创建重复的 `ToolCall` 和 `Block`。

当前 DeepSeek Provider 一次发完完整工具调用，所以不会触发。但这是 goai 上层应防御的边界，且未来接入其他 Provider 时可能暴露。

**建议与代价**：在收到 ChunkToolCall 时检查 `calls` 中是否已有同 ID 的条目，有则合并 args。改动限于 react.go 的 `request` 函数。也可在 goai 层面保证，那就标注为已知限制。

### 发现 12：host.Install 失败时先 Close 失败插件再 Close 全部已装插件——失败插件被 Close 两次

- 位置：`kernel/host/host.go:51-66`
- 维度：正确性
- 严重度：P2
- 归类：B 空白

**问题描述与证据**：

```go
func (h *Host) Install(p Plugin) error {
    err := p.Start(h)
    if err != nil {
        startErr := fmt.Errorf("host: start %s: %w", p.Name(), err)
        closeSelf := p.Close()       // ← Close 失败插件
        closeRest := h.Close()       // ← Close 全部已装插件
        return errors.Join(startErr, closeSelf, closeRest)
    }
    h.started = append(h.started, p)
    return nil
}
```

`h.Close()` 倒序 Close `h.started` 中的插件，不包含刚 Start 失败的 `p`（因为 `p` 还没 append 到 started）。所以 `p.Close()` 只被调用一次。✓

**撤回**：经复核，`p` 未进入 `h.started`，不存在重复 Close。此条不是问题。

### 发现 13：jsonl.Add 在 Sync 后未 fsync 目录——极端场景下崩溃可能丢失最后一行

- 位置：`kernel/persist/jsonl.go:211-243`
- 维度：正确性
- 严重度：P3
- 归类：C 故意

**问题描述与证据**：

`jsonl.Add` 写文件后调 `f.Sync()`，这只保证文件数据落盘。在大多数 Linux 文件系统上，新文件的目录项需要单独 fsync 目录 fd 才能在崩溃后恢复。当前未做目录 fsync。

这与设计书 §4 的描述一致：「进程崩了：已 Append 的还在，正在蹦、尚未 Append 的半截丢掉。」设计已接受此风险，且 jsonl 追加写依赖文件已存在（首次 Create 在 `openJSONL` 时的 `os.MkdirAll` 中完成），后续 Add 只是 O_APPEND 写入。

**建议与代价**：不修。当前行为与设计意图一致。若未来需要更强持久性保证，可在 Add 中加目录 fsync。

### 发现 14：machine-local.Run 用 exec.CommandContext 但未设置 Process Group

- 位置：`plugins/machine-local/local.go:48-71`
- 维度：演进阻力
- 严重度：P2
- 彸类：B 空白

**问题描述与证据**：

`machine-local.Run` 用 `exec.CommandContext(ctx, program, argv[1:]...)`，取消时 Go 默认只向直接子进程发 SIGKILL。若 bash -c 启动了孙子进程（如 `sleep 100 &`），SIGKILL 不会传递，孙子进程会变成孤儿。

阶段 5 子任务接入（spawn/wait）时，进程树管理会更关键。

**建议与代价**：在 `cmd.SysProcAttr` 中设置进程组（Linux: `Setsid: true`；Windows: `CREATE_NEW_PROCESS_GROUP`），取消时向整组发信号。改动限于 `local.go` 的 `Run` 函数。
