### 发现 1：React Loop 未累积流式工具调用参数
- 位置：plugins/loops/react/react.go:123-133
- 维度：正确性
- 严重度：P1
- 归类：B 空白
- 问题描述与证据：`ChunkToolCall` 分支为每个 chunk 直接构造完整 `ToolCall`，无跨 chunk 累积逻辑：

  ```go
  case provider.ChunkToolCall:
      call := session.ToolCall{
          ID:   chunk.ToolCallID,
          Name: chunk.ToolName,
          Args: chunk.ToolInput,
      }
      calls = append(calls, call)
  ```

  若 goai 按提供商协议分多个 chunk 发送同一工具调用的参数（部分 LLM 提供商如此），当前代码会为每个 chunk 新建一条 `ToolCall`，导致 `calls` 切片出现同 ID 重复条目、参数截断。DeepSeek 当前实现通常一次发完，故暂未触发，但切换或新增提供商时将暴露。
- 建议与代价：按 `ToolCallID` 累积 `ToolInput`，最终 chunk 到达后才拼入 `calls`。改动限于 `react.go` 的 `request` 方法，约 15 行；不影响 Runner、Session 或其他 Loop。

### 发现 3：Session 分叉指针不持久化——重启后丢失
- 位置：kernel/session/store.go:80-91
- 维度：正确性
- 严重度：P2
- 归类：B 空白
- 问题描述与证据：`Store.Get` 从磁盘加载后，将 `head` 设为文件顺序最后一个节点：

  ```go
  for _, node := range tree.Nodes {
      sess.nodes[node.ID] = node
      sess.head = node.ID  // 每个节点都覆盖，最终是最后追加的
  }
  ```

  若用户在运行期间调了 `Branch(id)` 移动光标到早期节点，重启后光标回到最后追加节点——分叉指针丢失。STATUS.md 将「Session 分叉」列为阶段 5 待做，当前 `Branch` 方法仅操作内存。代码逻辑自洽，但无文档声明此限制。
- 建议与代价：在 `Store.Get` 加载时从元数据恢复 `head`（需在 `Meta` 增加 `HeadID` 字段），或在 STATUS.md / 设计书明确标注 v1 分叉指针不跨重启。前者改动波及 persist 元数据格式与迁移；后者仅文档。

### 发现 5：chat.js 全量 innerHTML 重绘——长对话性能衰减
- 位置：surface/web/static/chat.js:276
- 维度：3
- 严重度：P2
- 归类：B 空白
- 问题描述与证据：`paint()` 每次调用都重建整个 `thread.innerHTML`：

  ```js
  thread.innerHTML = orderedItems().map(...).join("");
  ```

  每次 Delta（逐字输出时约每 50ms）都触发完整 DOM 重建。百条以上消息时浏览器重排成本显著，可感知卡顿。
- 建议与代价：短期可在 `paint()` 做增量更新（仅 append 新条目、更新最后 assistant 卡）；中期可引入虚拟滚动。前者改动限于 `chat.js` 的 `paint` 函数，约 40 行重写；后者架构变化较大。v1 可接受现状，标注为后续优化。

### 发现 7：Dock ID 校验用正则，其他登记处用纯空检查——风格不统一
- 位置：plugins/products/chat/docks.go:10, plugins/products/chat/panels.go, plugins/products/chat/message_actions.go
- 维度：3
- 严重度：P3
- 归类：B 空白
- 问题描述与证据：`DockRegistry` 用 `dockIDPattern = regexp.MustCompile(...)` 校验 ID 格式为 `[a-z][a-z0-9-]*`，而 `PanelRegistry` 和 `messageActionRegistry` 仅检查 `strings.TrimSpace(definition.ID) == ""`。同为登记处 ID，校验力度不同。
- 建议与代价：统一——要么所有登记处都加格式正则（推荐小写 kebab-case），要么仅保留非空检查。前者需在各 registry 加 regexp 并更新已有 ID；后者删掉 `dockIDPattern`。改动约 10 行。

### 发现 8：SSE History + 实时事件一致性无集成测试
- 位置：plugins/products/chat/handler.go:418-473
- 维度：7
- 严重度：P2
- 归类：B 空白
- 问题描述与证据：设计书 §13 要求"刷新或重新打开会话时，Web 的 History HTTP 接口返回耐久消息 JSON，仍交给同一个 paint()；Run 结束后 History 与 SSE 的最终状态一致"。当前仅有 `docks/demo` 的 SSE 集成测试，无覆盖「History 快照 + SSE 实时事件」在 Run 进行中/结束后的数据一致性。若 Runner Append 时序或 eventHub 分发逻辑出问题，前端会看到消息跳跃或丢失。
- 建议与代价：增加一个集成测试：启动 Run → 中途读 History → 验证 History 条目 ≤ SSE 已收到的耐久消息 → Run 结束后再读 History 验证一致。需在 `chat_test.go` 加约 60 行。

### 发现 9：Runner.Start 丢弃 runOne 返回的错误
- 位置：kernel/runner/run.go:110
- 维度：正确性
- 严重度：P2
- 归类：B 空白
- 问题描述与证据：

  ```go
  go func() {
      defer r.end(sessionID, current)
      _ = r.run(ctx, sessionID, input, current)
  }()
  ```

  `_ =` 显式丢弃错误。`runOne` 内的 `run-ended` 事件会携带错误状态（`RunFailed` + `errorText`），所以 UI 能看到失败，但调用方（HTTP handler）拿不到具体错误——`Start` 总返回 nil。对 v1 而言这是合理取舍（Run 是后台任务，错误走事件流），但应文档化。
- 建议与代价：在 `Runner.Start` 的 Go doc 注释中明确说明"错误通过 RunEvent 传递，不返回给调用方"。仅文档。

- **维度2（职责清晰度）**：A/B 形态使用正确；Chat 的三个插槽统一挂一个 `chat.Service` 键符合设计书"Chat 专属插槽由 Chat 自己提供的登记处管理"。

- **维度7（测试缺口）**：四个工具插件和 machine 契约包零测试是最大缺口；eventHub 慢客户端断连、SSE+History 一致性缺少集成测试。
