# 代码审查任务书（阶段 1–4C）

更新日期：2026-09-02。本目录存放多 Agent 并行审查的报告；每个 Agent 的产出
是本目录下一个以 UUID 命名的 Markdown 文件。任务书本身不存审查结论。

---

## 派发说明（给 Lucy，Agent 不用读这节）

**同题合审**：所有 Agent 拿到**一模一样**的任务书、审**一模一样**的全部范围。
目的不是分工覆盖，而是独立交叉验证——规避单一审查者注意力机制带来的
「错误但逻辑自洽」的发现。汇总规则：

- 两个以上独立报告都出现的发现 → 高置信，直接进确认清单
- 只有一个报告出现的发现 → 存疑，逐条人工复核（或再派一轮专门验证）
- 建议派 3–5 个同题 Agent；汇总由主会话完成后做

## 任务书（以下内容发给每个 Agent，一字不改，人人相同）

你是一次**同题合审**中的一员：多个审查者拿着与这份完全相同的任务书、
独立审查同一个代码库。你是**只读审查者**：不修改任何代码，
不提交，不重构。你的全部产出是一个 Markdown 审查报告。

### 独立性纪律（最重要的一条）

不要读取 `learn/审查报告/` 目录下的任何其他报告，也不要寻找其他审查者的
痕迹。你的价值恰恰在于**独立**得出结论——参考别人会让多个审查者的错误
变得一模一样，交叉验证就失效了。

### 基准文档（先读，再读代码）

1. `AGENTS.md` —— 铁律与代码规范，最高基准
2. `learn/设计书.md` —— 产品与架构的唯一总设计
3. `STATUS.md` —— 当前进度声称（需要核对真伪）

先从这三份建立「规则清单」，再读代码。每条发现必须注明依据或归类。

### 审查范围

`kernel/`、`surface/web/`、`plugins/`、`surface/web/static/*.js`、`cmd/harness/`。
未实现的阶段（5+）只作为「演进阻力」评估的输入，不在审查范围。

### 优先维度（有先后）

1. 架构是否清晰（分层、依赖方向、服务表形状）
2. 职责是否清晰（一个东西只干一件事；A 整份服务 / B 登记处形态是否用对）
3. 风格是否统一、还能不能再统一（命名、文件拆分、词汇表：登记处/插槽/活对象/数据/契约）
4. 是否符合文档规定——**双向**：代码违反文档 + 文档与现实脱节（STATUS.md 声称的东西是否属实）
5. 闭门造车：自己造了生态已有现成轮子的地方，是否因此造成问题
6. 过度设计：哪里还能更克制（多余的接口、预建的插槽、没主人的抽象）

**置顶规则**：确认的正确性问题（并发竞争、错误路径、数据一致性、事件顺序）
无视以上排名，永远排最前。存疑的不算——必须写出具体的失败场景才算确认。

### 补充维度

7. 承重墙测试缺口：哪些逻辑一旦改坏不会有任何东西报警
8. 下一阶段阻力：分叉 / 轨迹页 / 子任务接入时，现在的代码哪里会撞墙

### 判定规则（每条发现必须三选一归类）

```text
A 违规   违反 AGENTS.md / 设计书明文规定（注明哪条哪句）
B 空白   文档没规定，但可以更统一 / 更简洁
C 故意   文档规定的刻意取舍 → 列入「不修清单」，一句话带过，不展开
```

没有 C 类归档，审查会把项目的故意设计（注释中文、服务名硬编码、接口默认没有等）误报成问题。

### 参考项目（只用于维度 5 对照）

`reference/deepseek-harness/` 和 `reference/pi/` 已建 codegraph 索引，
查阅优先级：项目文档(docs) > codegraph > 直接读源码。`reference/htmx/docs/`
与 `reference/templ/docs/` 是技术文档。

约束：参考项目只用来回答「这个问题业界有没有现成解法、我们造的轮子是否
造成了实际伤害」，**不是对照答案**——它们的设计很多是我们明确不抄的
（见设计书 §18）。禁止建议「像 DSH 那样」「像 pi 那样」作为修改方案。

### 允许执行的命令

只读命令和测试：`go test ./...`、`go test -race ./...`、`go vet ./...`、
`node --test surface/web/static/test/*.test.js`、grep / find / 读文件。
禁止：任何写代码的命令、`go tool templ generate`、`npm run web:build`、git 写操作。

### 输出要求（严格遵守）

1. 生成文件名：执行 `uuidgen | tr 'A-Z' 'a-z'` 取小写 UUID，报告写到
   `learn/审查报告/<uuid>.md`
2. 报告开头必须写：UUID、日期、审查者身份（哪个 Agent）
3. 每条发现的格式：

   ```text
   ### 发现 N：<一句话标题>
   - 位置：path/to/file.go:行号
   - 维度：1–6 / 正确性 / 测试缺口 / 演进阻力
   - 严重度：P0（正确性）| P1（应修）| P2（可更统一）| P3（记录即可）
   - 归类：A 违规 | B 空白 | C 故意
   - 问题描述与证据：（引用代码原文）
   - 建议与代价：（怎么改 + 改动波及面）
   ```

4. 报告末尾三件套：
   - 修正清单（按严重度排序）
   - 不修清单（C 类归档 + 理由）
   - 总评（每个审查过的维度一句话）
5. 全部维度都要审，**不要因为「可能别人也审了」而省略或加深某一块**——
   每个审查者的覆盖面一致，重合度才有统计意义；报告独立成篇，不依赖其他报告可读。

### 禁止

不顺手重构；不提议新功能；不引入参考项目的机制作为修改方案；
不修改代码！
**不调用 subagent / 任务转包工具**——审查必须由你自己一次注意力独立完成。
不确定的标注「存疑」单独列一节，不混入确认清单。
