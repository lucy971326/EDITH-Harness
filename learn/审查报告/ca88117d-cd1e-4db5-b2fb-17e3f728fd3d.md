### 发现 1：Steer 被接受后若 Run 失败，用户输入被静默丢弃
- 位置：`kernel/runner/run.go:115-128`（run 循环）、`kernel/runner/run.go:223-239`（end 不清理 steers）、`kernel/runner/steer.go:70-82`（takeSteers 只在 Checkpoint 消费）、`plugins/loops/react/react.go:45-62`（错误直接 return，不经过 Checkpoint）
- 维度：正确性（错误路径、数据一致性）
- 严重度：P0
- 归类：A 违规（违反设计书 §11 对 Steer 路径定下的验收标准「不会成功后丢失」；该句字面针对最终检查点关闸场景，但「Steer 成功返回 ⇒ 消息终将入账」是整条路径明文承诺的不变量）
- 问题描述与证据：

  `Steer` 受理成功后只是入队：
  ```go
  current.steers = append(current.steers, session.UserMessage{Blocks: cloneBlocks(input.Blocks)})
  return nil
  ```
  队列只在 Loop 调 `Checkpoint` 时被消费。而 React Loop 的每个错误出口都直接返回、不再触碰 Checkpoint：
  ```go
  assistant, calls, err := l.request(ctx, invocation, history, definitions, stepSeq)
  if err != nil {
      return err   // 已入队的 Steer 没有任何 Checkpoint 会来取
  }
  ```
  `run` 循环在无 FollowUp 时直接返回，`end()` 只关闸、不清账。**具体失败场景**：用户在模型流式输出期间发 Steer（HTTP 204，`chat.js:323` 随即清空输入框），随后 LLM 流出错（网络断、余额尽、`ChunkError`）→ `request` 返回错误 → `react.Run` 未到 Checkpoint 就 return → `run-ended(failed)` → 这条 Steer 不落账、不发事件、无任何回执，用户消息无痕消失。Steer 产生于两次 Checkpoint 之间的窗口（正好是用户最可能插话的长回复/长工具执行期），而 LLM 流失败是日常错误，场景现实。
  **第二场景（行为不一致）**：同一窗口里若恰好排了 FollowUp，`run()` 会进入下一轮 `runOne`；`openSteering()`（steer.go:106-111）只重置 `stopped`/`steeringClosed`、**不清 `current.steers`** → 上一轮遗留的 Steer 在下一轮第一个 Checkpoint 被追加，且 RunID 记为下一轮——消息不丢但归属错位。同一条 Steer 的命运取决于是否恰好存在 FollowUp，两种路径行为不同。
  （对照：Stop 取消时丢弃队列属于取消语义，设计书 §11「打断正在流的半句是 Stop」，可接受；问题在 failed 路径。）
- 建议与代价：`runOne` 错误返回时（或 `end()` 里区分状态），对 failed 的 Run 把未消费的 steers 补 `Append` 并发布 `Message` 事件；cancelled 可维持丢弃。约 20 行 + 一个失败路径测试；react 不动。另建议 `openSteering()` 明确决策是否清空遗留队列，消除两场景不一致。

- 严重度：P1
- 归类：A 违规（违反 AGENTS.md 对活对象并发安全的通用要求——同仓库同类结构已自证应有纪律，见证据）
- 问题描述与证据：

  ```go
  // PanelRegistry —— 无锁
  type PanelRegistry struct {
      panels map[string]Panel
  }
  ```
  而 kernel 里同形状的登记处全部带锁（`kernel/tools/registry.go:14-17`、`kernel/loops/registry.go:10-13`、`kernel/skills/registry.go:10-13` 均有 `sync.RWMutex`）。Web 服务器在 `web.Start` 就开始 accept，`chat.Start` 注册路由后页面即可访问；此后 `paneldemo.Start` / 测试里的 `docks-demo` 才向这三个 map 写入。**具体失败场景**：进程重启时，残留的已打开浏览器标签页（HTMX SSE 自动重连、或用户刷新）在「chat 路由已活、paneldemo 尚未装完」的窗口内 GET /chat → `pageData` 读 `h.registry.Panels()` 与 `RegisterPanel` 的 map 写并发 → Go 运行时 fatal error「concurrent map read and map write」，整个进程崩溃，不可恢复。窗口是毫秒级，但旧标签页自动重连是真实、反复发生的行为。chat 自身在路由注册前写 `copyMessageAction` 是有序的（经 ServeMux 锁建立 happens-before），风险只在「路由已注册之后才 Start 的填充者」。

### 发现 8：流式期间每个 delta 全量重绘时间线并强制滚底
- 位置：`surface/web/static/chat.js:275-281`
- 维度：维度 6（克制）/ 正确性外围体验
- 严重度：P2
- 归类：B 空白
- 问题描述与证据：
  ```js
  function paint() {
    thread.innerHTML = orderedItems().map(...).join("");

  ```
  每个 text-delta 触发一次整条时间线的 innerHTML 重建 + 无条件 `scrollIntoView`。长回复时用户无法上滚回看（每来一个字就被拽回底部），且每 token 一次 O(n) DOM 重建。

## 不修清单（C 类归档）

- **`Runner.FollowUp` 方法存在**：不违反铁律 4「不要 Chat.Followup」——禁令针对聊天层的隐式 Followup/Inbox；设计书 §11 明文定义 Runner.FollowUp 且 STATUS 如实声称。
- **初始用户消息先于 `run-started` 发布**（run.go:164-169）：顺序有测试锁定（`wantKinds[0]=Message`），设计书未规定两者先后，前端已兼容。
- **run-ended 用 `context.Background()` 发布**（run.go:177）：保证取消后结束事件必达，正是设计书 §2 的意图。
- **`persist.Save` 无生产调用者**：设计书 §4 明文预留（「Save 留给换后端、迁移、补快照」）。
- **`Store.Rename` 无 UI**：设计书 §4 Session API 列表明文包含。
- **`AfterEntrySeq` 锚点不随 Steer 前移**：有专门测试锁定（`TestRunKeepsInitialAnchorAfterSteer`），前端切段靠 entry 自身 seq，语义自洽。
- **服务名硬编码字符串 + 泛型 `Resolve`、注释中文、commit 双语、接口默认没有、启动时固定 Register 无注销（`events.Subscribe` 的幂等 unlisten 除外）**：AGENTS.md 明文规定。
- **`tools.Tool` 接口含未导出方法 `call`（封闭接口）**：设计书 §7「Tool 作者只写参数结构体和 tag，不手写 JSON Schema」的实现手段。
- **demo 插件 import `plugins/products/chat`**：填充者 import 定义者，设计书 §14「Chat 专属插槽由 Chat 自己提供登记处」的既定形状。
- **jsonl `Add` 逐条 `f.Sync()` 写穿、`Save` 不 fsync**：设计书 §3「Append 已经写穿完整条目」；Save 仅迁移用，崩溃语义按设计接受。
- **一轮只服务一个实时 UI、轨迹页/分叉 UI 未实现**：设计书 §4/§14 与 STATUS 均如实标注为阶段 5。
- **无日志、错误只返回**：符合 AGENTS.md「普通包只返回错误」；main 在进程边界打印一次。
- **`live-mode` 默认 steer 硬编码**：设计书 §11「默认选择属于 UI 插件的全局设置」——v1 尚无设置系统，暂无所属。

## 总评（按维度）

1. **架构清晰度**：好——分层与依赖方向零违规（kernel 不碰 plugins/surface，填充者只 import 定义者），服务表形状与设计书逐键对得上，组装顺序与 AGENTS.md 完全一致。
2. **职责清晰**：好——A/B 形态用得对（machine 契约与提供者分离、tools/loops/skills 纯登记处），唯一例外是 chat 三个登记处的并发纪律与 kernel 同类结构不一致（发现 2）。
3. **风格统一**：中上——词汇表（登记处/插槽/活对象/数据/契约）贯彻得很一致，注释中文齐整；主要裂痕是 34 处一行式 if err（发现 6）与 chat.js 一处 Tab（发现 11）。
4. **符合文档（双向）**：好——代码未见违反设计书硬性规定；反向有四处小脱节（发现 12/13/14 + yaml 形状），STATUS 的可核对声称全部属实。
5. **闭门造车**：无实质伤害——JSON Schema 用 invopop/santhosh-tekuri、LLM 协议用 goai、SSE 服务端手写仅 12 行属合理体量，未发现自造轮子造成实际问题的场景。
6. **过度设计**：轻微——两处无主 API（发现 7）、一个无主 multipart 口子（发现 10）；其余接口都能指出当班调用者。
7. **承重墙测试缺口**：最薄弱项——kernel 侧（runner/session/persist/tools）覆盖扎实且测到并发与错误路径，但聊天画面的全部正确性压在零测试的 chat.js reducer 上（发现 3），SSE 主通路端到端也无用例（发现 4）。
8. **下一阶段阻力**：小——分叉（Branch + Entry 已备好、copy 动作的 RunID+BoundaryEntryID 协议可沿分叉成立）、轨迹页（Entries 含 RunID/seq 信息完备）、子任务（Runner 一 session 一 live 的约束与 spawn 按子 session 建 Run 的设计兼容）；当前代码没有会撞墙的焊死点。
