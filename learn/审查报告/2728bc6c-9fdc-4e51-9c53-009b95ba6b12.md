### 发现 1：停止打断工具执行会在账本留下没有结果的 tool-call，此后该会话每一轮都会失败

- 位置：plugins/loops/react/react.go:167-169（`tools.Call` 出错直接 return，不再 Emit 结果消息）；kernel/runner/run.go:136-138（`defer cancel()` 的取消链）；kernel/llm/messages.go:69-78（tool-call 原样转 goai，无修补）；goai v0.9.8 `provider/normalize.go:10-23` 的孤立 tool-call 修补只被 `provider/anthropic/anthropic.go` 与 `provider/bedrock/converse.go` 调用，DeepSeek 走的 `provider/deepseek/deepseek.go:60` → `internal/openaicompat` 路径没有接。
- 维度：正确性
- 严重度：P0
- 归类：B 空白
- 问题描述与证据：react 的执行顺序是「assistant 消息（含 tool-call 块）先落账 → 逐个执行工具」。工具执行期间 ctx 被取消时：

  ```go
  result, err := l.tools.Call(ctx, tools.Call{...})
  if err != nil {
      return session.Message{}, err   // react.go:167-169，tool-result 消息永远不会 Emit
  }
  ```

  `tools.Call` 返回非 nil error 的唯一路径是 ctx 取消（handler 错误已被 registry 转成 `Result{IsError}`）。于是账本里永久留下一条带 `tool-call` 块、没有配对 `tool-result` 的 assistant 消息。具体失败场景：用户在 bash 长命令执行中点「停止」，或进程在工具执行中收到 Ctrl-C（`Runner.Close` 会取消所有 Run 后退出）→ 下一次在该会话发消息，`History()` 含未配对 tool-call → 转成 goai 请求后 DeepSeek（OpenAI 兼容协议要求每个 tool_call_id 必须紧跟对应 tool 消息）返回 400 → RunFailed；由于坏条目永远留在 History 里，之后每一轮都重复失败，会话被「锁死」，只能手工改数据文件。UI 侧同场景下该工具卡永远显示「执行中」（chat.js `toolBlock`：无 result 时 `status = "执行中"`）。
- 建议与代价：在 react 的 `tools.Call` 出错分支（至少覆盖 ctx 取消）也 Emit 一条 `IsError` 的 tool-result 消息再返回错误——`Session.Append` 不依赖 ctx，取消后仍可落账；改动仅 react.go 一个分支 + 补一条「取消时结果也入账」的测试。另一方向是把 goai 的 `NormalizeToolMessages` 接到 openaicompat，但那是依赖库的事。波及面：小。

### 发现 2：History 重载窗口内的 delta 重放会把已入账文本重复拼一次

- 位置：surface/web/static/chat.js:217（`block.text = (block.text || "") + (event.text || "")`）、chat.js:300-315（`loadHistory` 的 hydrating/queuedEvents 机制）、chat.js:359-368（`htmx:sseBeforeMessage` 中 `if (hydrating) queuedEvents.push(item)`）
- 维度：正确性
- 严重度：P1
- 归类：B 空白
- 问题描述与证据：SSE 每次连接/重连触发 `loadHistory()`；fetch 进行中到达的 run 事件进入 `queuedEvents`，fetch 完成后先 `apply(entries)` 再按序重放队列。失败场景：Run 进行中 SSE 断线重连（htmx sse 扩展自动重连触发 `htmx:sseOpen`），某一步的 text-delta 在 fetch 发出后、快照生成前到达——这些 delta 既进了队列，其所属 assistant 消息又已在快照里；重放时 `blockFor` 找到 `registerAssistant` 刚用耐久消息建好的块，`+=` 把同一段文本再拼一遍，消息出现重复片段，直到下一次 history 重载才恢复。耐久 message 事件本身有 `entry.id` 去重（chat.js:185），delta 没有。
- 建议与代价：重放队列前丢弃「其 step 已有耐久消息」的 delta（按 runID+stepSeq 查 `registerAssistant` 已建的 steps），或给 delta 事件带上可比较的耐久水位。改动仅 chat.js 一个函数；需要补前端测试（见发现 3）。波及面：小。

### 发现 6：Stop 取消当前 Run 后，队列里的 FollowUp 仍会自动开下一轮

2. **职责**：A/B 形态用对（machine 契约在 kernel 由提供者挂 A；四个 B 都是纯登记处；chat 三个页面插槽收在 chat.Service 不占 Host 键）；仅发现 6 的 Stop/FollowUp 叠加语义与发现 11 的薄转发层有模糊处。
3. **风格**：类型注释（数据/契约/活对象）、文件拆分、中文注释、词表高度统一；残留 32 处 err 单行（A 类）与 New/NewPlugin 两套构造名。
4. **文档符合度**：代码违反文档只发现风格一项；反向的文档滞后有三处（发现 5/13、enable 未实现的既定计划）；STATUS 的全部进度声称与验证命令经复跑核对属实。
5. **闭门造车**：schema 生成与校验（invopop/jsonschema + santhosh-tekuri/jsonschema）、templ、路由（stdlib mux）、json/yaml 均用现成轮子；自写的 events 总线、SSE 写流、前端 reducer 都是小体量且各有不可替代的职责，未发现造成实际伤害的自造轮子。
6. **过度设计**：整体克制；最接近越线的是三个单实现接口（发现 8）与两处薄包装（发现 11），均无害。
7. **测试缺口**：后端承重墙（runner 事件顺序/取消/检查点、tools 校验与权限、react 循环、persist、session 分叉、hub）覆盖扎实且用例贴着失败场景写；两块无报警区是前端 reducer（发现 3）与 run 事件 SSE 流（发现 4）。
8. **演进阻力**：分叉（Branch 只动光标）、轨迹页（Session+RunEvent 即可拼）、子任务（Runner.live 按 session 隔离，Spawn/Wait 预留位清晰）、模型/档位后续修改（需补一条 sessionSettings Put 路由）接入路径都畅通；唯一会向未来阶段扩散的债务是发现 1——账本一旦留脏，分叉页/轨迹页/子任务读到的都是同一段坏 History。
