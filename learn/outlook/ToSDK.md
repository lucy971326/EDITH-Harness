# 展望：内核 SDK 化

记录于 2026-09-02。讨论结论：内核 + 基础功能完成后，可以发布为库 / SDK，
并配一套 Skills 教 AI 开发插件。这是展望，不是计划——不动手，等 v1 之后。

## 为什么天然是 SDK 形态

不是目标，是纪律的副产品。当初为「架构不腐烂」定的边界，对外恰好就是 API：

1. **Host + Plugin 就是库 API。** 别人当库用，写的就是 `host.NewHost()` + `Install` 自己的插件名单 + 自己的 `cmd/main`。和设计书 §2「另做一个产品 = 另写一个 main」是同一句话。
2. **依赖方向已经画好了库边界。** kernel 不得 import plugins、定义者不得 import 填充者——内核对使用者零认知，能独立于任何插件编译通过。
3. **插件契约就是普通 Go 接口。** 没有注册魔法、反射、注解。第三方体验 = import 定义者包 → 实现接口 → `Start` 里 Register。
4. **不违反铁律。**「无动态插件」防的是终端用户运行时加载代码；SDK 用户是开发者，编译后交付，和 `plugins/` 目录无本质区别。

## 关键加分项：契约小到 AI 能学会

铁律全是「让契约变小」的：接口默认没有、不预建插槽、`Start`/`Close` 两个方法。
插件的正确写法空间非常小 → AI + Skills 能稳定写出正确插件。
充满反射和注解魔法的框架做不到这一点。这是 AI 时代 SDK 的差异化位置。

## 差什么

| 缺口 | 说明 | 解法 |
|---|---|---|
| API 面标注 | 现在 kernel 全部「公开」 | 明确哪些是承诺不破坏的公共 API（host、各契约包），哪些内部 |
| Resolve 运行时错误 | 字符串键 + 泛型断言，契约改名 = 组装期才报错 | 契约包导出标准键常量 + 好的错误信息，不推翻设计 |
| 版本化 | 改契约是对 SDK 用户的破坏 | go.mod v0 发布，对改契约建立敬畏 |
| 外部验证 | 没有第二个消费者之前不知道缺什么 | 第一个外部开发者写插件成功之前，不谈正式 SDK |
| Skills 包 | 插件开发的正确姿势要可分发 | 见下 |

## Skills 包（教 AI 开发插件）

内容已经写完 80%，蒸馏即可：

```text
SKILL.md     = AGENTS.md 的四问话术 + A/B 服务形态 + 文件拆分规则
examples/    = tools/bash（最小插件）、docks/demo（填 Chat 槽位）
checklist    = 「Run 是否取尽 Steers？不取尽不准 Register」等验收项
```

## 明确不做：插件市场

讨论后否决（2026-09-02），理由存档：

1. **工具市场**不是本项目意义上的插件扩展——MCP 走的是进程配置，是本来就有的扩展模式，不占「插件」这个概念。
2. **面向最终用户的安装 CLI**（`harness add` → 自动改清单 → 自动编译）身份错位：能用它的人必然有 Go 工具链和源码，那他就是开发者，不需要这层包装；真正的用户会被编译报错劝退。体验是动态的，内核是静态的，硬捏必拧巴。
3. 结论：**不做市场。路线是 SDK + Skills**——开发者拿到契约和 Skills，自己动手写插件、AI 辅助开发。`harness add` 这类依赖管理工具属于 SDK 发布之后的开发者便利工具，不是产品功能。

## 时机（按自己的纪律来）

```text
现在         不动手。先完成阶段 4/5——没被自己狗食过的 API 不要冻结
v1 之后      仓库作为 Go 库发布（v0），写一个独立示例插件验证 import 边界
出现外部用户  把 AGENTS.md 蒸馏成 skill 包发布；此时才知道 AI 开发者卡在哪
```

一句话：门口就是路，但现在不迈。SDK 是 v1 之后的选项，不是现在的分心。
