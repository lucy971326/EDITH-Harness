# 阶段 4：页面插槽

## 进度

阶段 4 不是一次把所有页面扩展都做完，而是逐个验证页面插槽边界。

当前第一版五个页面插槽基础设施已全部竣工：

```text
message.actions  → 消息卡片下方的标准动作（已实现复制）
sidepanel        → keyed 右侧面板登记处（已实现 demo）

```

各插槽的丰富填充物（如消息分叉、真实文件面板等）留在后续业务演进中逐步扩展。

## 消息下插槽：message.actions

### 目标

让 Chat 统一绘制消息卡片下方的动作按钮，插件只登记动作和执行逻辑。浏览器只提交卡片身份，真正的消息内容由 Chat 从当前分叉账本重新读取。

```text
动作插件 → chat.Service.RegisterMessageAction(动作)
paint()   → 用户卡 / 已完成助手卡下方画按钮
POST      → Chat 校验卡片身份 → Execute → JSON
```

### 契约

```go
// 数据。一张消息卡片的类型。
type MessageCardType string

const (
	MessageCardUser      MessageCardType = "user"
	MessageCardAssistant MessageCardType = "assistant"
)

// 数据。一个已登记消息动作的显示与适用卡片类型。
type MessageActionDefinition struct {
	ID      string            `json:"id"`
	Name    string            `json:"name"`
	Icon    string            `json:"icon"`
	Order   int               `json:"order"`
	Targets []MessageCardType `json:"targets"`
}

// 数据。浏览器提交给消息动作的一张卡片身份。
type MessageActionTarget struct {
	CardType        MessageCardType
	EntryID         string
	RunID           string
	BoundaryEntryID string
}

// 数据。Chat 已验证后交给消息动作的当前分叉事实。
type MessageActionContext struct {
	SessionID string
	Entries   []session.Entry
	Target    MessageActionTarget
}

// 数据。一项消息动作成功后的浏览器回包。
type MessageActionResult struct {
	Text string `json:"text"`
}

// 契约。一个可填入 Chat 消息卡片下方的标准动作。
type MessageAction interface {
	Definition() MessageActionDefinition
	Execute(context.Context, MessageActionContext) (MessageActionResult, error)
}
```

- `RegisterMessageAction` 拒绝空字段、无目标类型和重复 `ID`。
- `MessageActions` 按 `Order`、再按 `ID` 稳定排序。
- Chat 把动作定义放入页面数据；`paint()` 根据 `Targets` 统一绘制按钮。
- 服务端不相信浏览器传来的正文，只相信并校验 `EntryID`、`RunID` 和 `BoundaryEntryID`。

### 内置复制动作

当前只有一个内置动作 `copy`，同时支持用户卡和助手卡。

```text
用户卡：按 EntryID 取该用户消息的 text Block

助手卡：
  RunID + boundaryEntryID 定位同一 Run 段
  → 从边界用户 Entry 开始向后扫描
  → 遇到下一条同 RunID 的用户 Entry 停止
  → 只取最后一条有正文的 assistant 消息
```

复制助手卡时：

- 忽略 reasoning。
- 忽略工具调用和工具结果。
- 忽略工具调用前的临时文字。
- 不把相邻 Steer 段混进来。
- 运行中的助手卡不显示复制按钮，服务端也返回冲突错误。

成功响应固定为 JSON：

```json
{"text":"要复制的正文"}
```

浏览器拿 `text` 写入 Clipboard。动作路由不改 Session，也不把复制文本写回账本。

路由形状为：

```text
POST /chat/{sessionID}/message-actions/{actionID}
```

## 右侧面板插槽：sidepanel

### 目标

实现 Chat 专属的 `sidepanel` keyed 登记处。

```text
Chat：Tab 壳、开关、宽度、实例规则
面板插件：登记类型、画自己的内容
浏览器：当前 Tab / 宽度等临时状态
Session：完全不碰
```

首版只安装一个独立 `demo` 面板，验证插件能填入 Chat 的登记处；不实现文件、终端、浏览器或编辑器。

### 契约

Chat 启动时在 Host 的 `"chat"` 键提供 `chat.Service`。这是 Chat 产品自己的登记处 B，不是 Web 公共插槽。

```go
// 数据。一个已登记面板类型的显示与默认打开信息。
type PanelDefinition struct {
	ID                 string
	Name               string
	Icon               string
	Order              int
	DefaultInstanceKey string
	DefaultTabTitle    string
}

// 数据。浏览器当前打开的一个面板实例。
type PanelTab struct {
	Type        string
	InstanceKey string
}

// 数据。渲染面板所需的当前会话事实。
type PanelContext struct {
	SessionID string
	Workspace string
}

// 契约。一个可填入 Chat 右侧面板的类型。
type Panel interface {
	Definition() PanelDefinition
	Render(PanelContext, PanelTab) (templ.Component, error)
}
```

- `RegisterPanel` 拒绝空字段和重复 `ID`。
- `Panels` 按 `Order`、再按 `ID` 排序，和产品入口一致。
- 右栏 Tab 的身份是 `(Type, InstanceKey)`：相同身份聚焦已有 Tab；不同身份新建 Tab。
- `PanelTab` 不携带标题或图标。Chat 永远从已登记的 `PanelDefinition` 取得默认标题和图标。

### 页面与路由

- Chat 顶栏新增“打开面板”按钮；会话页初始时右栏关闭。
- 右栏由 Chat 固定渲染：Tab 栏、`+` 菜单、关闭、拖拽调宽和空状态。
- `+` 菜单只列出已登记类型。关闭只是隐藏，当前页面的 Tabs 和宽度仍留在浏览器内存；刷新或切换会话即丢弃。
- 面板内容通过 Chat 专用片段路由取得。浏览器只传 `type` 与 `instance`；路由先确认类型已登记，再调用该 `Panel.Render` 并输出 `templ.Component`。未知类型返回 404。
- `demo` 的默认实例键为 `main`（完整 Tab 身份为 `demo:main`），页面文案为「面板登记已就绪」。
- 首版只验电脑端；右栏不做手机布局。

未来 `file` 类型可以使用 `file:/a.go`、`file:/b.go` 等实例键。对应面板插件负责校验自己的实例键；Chat 只执行通用 Tab 规则。

### 演示插件

新增独立 `plugins/panels/demo`：它只 Resolve `chat.Service`、登记 `demo` 类型并返回静态 templ 内容。应用入口在 Chat 后安装它，以真实页面验证外部插件边界。Chat 不 import 这个插件，也不认识 demo 的内容。

### 验收

- Go 测试：合法登记、重复/空字段拒绝、按 `Order / ID` 排序、demo 插件安装、未知类型 404、面板片段可渲染。
- 前端测试：使用两个不同实例键验证新开、同实例聚焦、切换、关闭及选中回退。
- 浏览器测试：默认关闭 → 顶栏打开 → `+` 打开 demo → 关闭再打开 → 拖拽调宽。
- 完成后运行全量 Go 测试、race、vet、前端语法/测试，并更新相关 README 与 `STATUS.md`。

### 不做

- 文件树、文件预览、编辑器、终端、浏览器。
- 将工具调用详情放进右栏。
- 将面板状态写入 Session。
- 为 demo 伪造多个实例或安装多个演示插件。

## 输入框上方插槽：dock

### 目标

在 Chat 输入框上方增加 Dock：Todo、Goal、Subagent 等插件可以登记一项持续状态，并在状态变化时实时更新页面。

```text
业务插件改变状态
      ↓
发布 DockChanged
      ↓
Chat 调用 Dock.Render()
      ↓
现有 SSE 直接发送 Templ HTML
      ↓
HTMX sse-swap 替换对应内容
```

Dock 只是 Chat 的 `list` 插槽，不保存业务状态，也不认识 Todo、Goal、Subagent。

### 边界

```text
Chat               提供 Dock UI 插槽：登记处、折叠外壳、排序、SSE 转发
填充 Dock 的插件    拥有或读取自己的状态，登记条目并提供 Render()
events             传递状态已变化的进程内通知
浏览器             保存当前页面的展开 / 折叠状态
Session            只保存对话，不保存 Dock 状态
```

是否落盘由业务插件决定，不属于 Dock 契约。本阶段不实现通用 Storage。

### 契约

```go
// 数据。一个已登记 Dock 条目的静态身份。
type DockDefinition struct {
	ID    string
	Name  string
	Order int
}

// 数据。渲染 Dock 所需的当前会话事实。
type DockContext struct {
	SessionID string
	Workspace string
}

// 契约。一个可填入 Chat 输入框上方的持续状态条目。
type Dock interface {
	Definition() DockDefinition
	Render(DockContext) (templ.Component, error)
}

// 数据。一个 Dock 条目的状态已经变化。
type DockChanged struct {
	SessionID string
	DockID    string
}
```

`chat.Service` 增加：

```go
RegisterDock(Dock) error
Docks() []DockDefinition
Dock(id string) (Dock, bool)
```

规则：

- `ID`、`Name` 必填，拒绝重复 `ID`。
- `ID` 只允许小写字母、数字和 `-`，并以小写字母开头；它同时用于 DOM ID 和 SSE 事件名。
- `Docks()` 按 `Order`、再按 `ID` 稳定排序。
- 不提供图标字段；Chat 使用浏览器原生的折叠标记。
- 没有插件填充 Dock 时，页面不渲染 Dock 区域。
- 一个已填入的条目如何表达“暂无内容”，由提供它的插件决定。

### 页面与 SSE

Chat 固定绘制每个 Dock 的 `<details>` 和标题，插件只绘制内容。条目首次出现时默认折叠；SSE 只替换内部内容，因此用户当前的展开状态不会丢失。

```html
<details>
  <summary>Todo</summary>
  <div sse-swap="dock-todo">
    <!-- Todo.Render() 生成的 HTML -->
  </div>
</details>
```

一个页面仍然只有一条 SSE 连接。把现有 `hx-ext="sse"` 和 `sse-connect` 放到消息区、Dock、输入框共同的外层元素上；这只改变 HTML 属性位置，不改变页面布局。

```html
<div hx-ext="sse" sse-connect="/chat/{sessionID}/events">
  <section>消息区</section>
  <section>Dock</section>
  <form>输入框</form>
</div>
```

SSE 消息分为：

```text
event: run            data: Runner JSON
event: dock-todo      data: Todo 的最新 HTML
event: dock-goal      data: Goal 的最新 HTML
```

这里的 `dock-{ID}` 只是浏览器传输地址，不是新的业务事件类型。业务插件仍然只发布强类型的 `DockChanged`。

### 更新与恢复

```text
插件提交状态成功
  → events.Publish(DockChanged{SessionID, DockID})
  → Chat 的回调只把通知放入该 Session 的页面队列
  → 对应 SSE Handler 调用 Dock.Render()
  → 写出 event: dock-{DockID} 和 Templ HTML
```

- 发布回调不能等待浏览器，也不能在业务写入完成前通知。
- 未登记的 `DockID` 不发送到浏览器。
- 一个 Dock 渲染失败不能关闭 SSE，也不能影响聊天消息；该条目显示简短加载错误，后续变化可以再次渲染。
- SSE 写 HTML 时必须正确处理多行 `data:`，不能假设 Templ 输出永远只有一行。
- 每次 SSE 首次连接或重连，在完成订阅后依次渲染并发送全部已登记 Dock 的当前内容；不增加 `snapshot`、`seq` 或额外恢复协议。
- 慢客户端继续沿用现有规则：队列满就断开，重连后重新取得当前 Dock 内容。

### 演示插件

新增独立动态 Demo 插件验证真实边界：

- Resolve `chat.Service`、`events`，登记一个 Dock。
- 使用内存保存按 Session 区分的演示计数。
- 状态变化后发布 `DockChanged`，验证页面收到新的 Templ HTML。
- 不写 Session、不使用 Storage、不启动后台任务。
- 只用于自动化测试，不安装到正常的 `cmd/harness`。

### 验收

- 登记：合法条目、非法 ID、空字段、重复 ID、`Order / ID` 排序。
- 页面：没有登记项时没有 Dock；有多个登记项时顺序正确且默认折叠。
- 实时：一个 Dock 变化只产生对应的 `dock-{ID}` HTML 事件，`run` 事件不受影响。
- 状态：更新内部内容不会替换 `<details>`，展开 / 折叠状态保持。
- 恢复：首次连接和重连都会得到所有 Dock 的当前内容。
- 隔离：事件只进入对应 Session 的 SSE 连接。
- 错误：未知 Dock 不发送；单个 Render 失败不关闭连接。
- 协议：多行 HTML 能通过 SSE 完整还原。
- Demo：跑通“状态变化 → events → Chat → SSE HTML → HTMX 替换”。
- 完成后运行 Templ 生成、Tailwind 构建、Go 全量测试、Chat race 测试、`go vet`、Node 测试和 `git diff --check`。

### 不做

- 通用 Storage 服务。
- Todo、Goal、Subagent 的真实业务。
- 图标系统。
- Dock 片段 GET 路由。
- Dock 专用 JavaScript。
- 第二条 SSE、WebSocket、JSON reducer。
- `snapshot`、`seq`、动态插件或运行时热插拔。
- Workspace / 全局范围的 Dock 广播；首版只按 Session 更新。

## 输入工具栏插槽：composer.actions

### 目标

在 Chat 输入框表单 `#composer` 底部工具栏左侧增加 `composer.actions` 插槽，供插件扩展输入辅助动作（如附件、模版快捷输入等）。

```text
动作插件 → chat.Service.RegisterComposerAction(动作)
Chat     → 在 #composer 底部工具栏左侧渲染 #composer-actions 容器
插件组件 → templ + 原生 HTML + HTMX
```

### 契约

```go
// 数据。一个已登记输入工具栏动作的静态身份。
type ComposerActionDefinition struct {
	ID    string
	Order int
}

// 数据。渲染输入工具栏动作所需的当前会话事实。
type ComposerActionContext struct {
	SessionID string
	Workspace string
}

// 契约。一个可填入 Chat 输入工具栏的扩展动作。
type ComposerAction interface {
	Definition() ComposerActionDefinition
	Render(ComposerActionContext) (templ.Component, error)
}
```

`chat.Service` 增加：

```go
RegisterComposerAction(ComposerAction) error
ComposerActions() []ComposerActionDefinition
ComposerAction(id string) (ComposerAction, bool)
```

规则与原则：

- `ID` 必填且合法（符合 `^[a-z][a-z0-9-]*$`），拒绝重复 `ID`。
- 精简契约：`ComposerActionDefinition` 不需要 `Name`，插件自绘按钮与文案。
- 排序：按 `Order`、再按 `ID` 稳定排序。
- 错误隔离：单个 Action 调用 `Render` 失败或返回 `nil` 时，Chat 捕获并跳过该条目，不破坏整个 ChatPage 渲染。
- 无嵌套表单：插槽位于 `#composer` 表单内部，严禁嵌套 `<form>`；选项和按钮必须使用 `type="button"`。
- 原生文件提交：表单包含 `<input type="file">` 时，前端保留 `FormData` 以原生 `multipart/form-data` 提交，服务端原生解析；提交成功后清空文件输入框。
- 极简 JS：除非必须操作浏览器临时状态（如将预设文本写入 `textarea`），尽量不写自定义 JS；优先原生能力。

### 演示插件

新增独立 `plugins/composers/demo`：

- Resolve `chat.Service`，登记 `demo` 动作。
- 渲染原生 `<details>` 下拉菜单，展开显示预设模版。
- 点击按钮使用极简内联 JS 将文本填入 `#composer textarea` 并聚焦，关闭 `<details>`。
- 已安装至 `cmd/harness/main.go`。

## Web 设置栏目插槽：settings.section

### 目标

在 Web 表面提供公共设置插槽与全局入口，供各插件登记自己的二级设置页面片段（如模型设置、沙箱设置、主题配置等）。

```text
设置插件 → web.Service.RegisterSettingsSection(栏目)
Web     → 左侧边栏底部固定「⚙ 设置」全局入口
主界面   → Master-Detail 左右双栏结构，左侧选择插件，右侧展示配置
```

### 契约

```go
// 数据。一个已登记设置栏目的静态身份。
type SettingsSectionDefinition struct {
	ID    string
	Title string
	Order int
}

// 契约。一个可填入 Web 公共设置页的插件栏目。
type SettingsSection interface {
	Definition() SettingsSectionDefinition
	Render() (templ.Component, error)
}
```

`web.Service` 增加：

```go
RegisterSettingsSection(SettingsSection) error
SettingsSections() []SettingsSectionDefinition
SettingsSection(id string) (SettingsSection, bool)
```

规则与原则：

- `ID` 必填且合法（符合 `^[a-z][a-z0-9-]*$`），拒绝重复 `ID`；`Title` 必填。
- 排序：按 `Order`、再按 `ID` 稳定排序。
- 精简契约：`SettingsSectionDefinition` 无需 `Icon`；接口直接 `Render() (templ.Component, error)`，不造空壳上下文。
- 错误隔离与防御：单个栏目渲染失败或返回 `nil` 时，右侧区域展示友好错误提示，绝不影响设置页整体。
- 保留 URL 与浏览记录：左栏切换使用 `hx-push-url="true"`，通过 HTMX 局部加载 `#settings-content`，刷新或前后导航不丢失当前选中项。
- 状态归属：插件自己管理设置状态；不写入 Session，不创建通用 Store。

### 演示插件

新增独立 `plugins/settings/demo`：

- Resolve `web.Service`，登记 `demo` 设置栏目与 `POST /settings/demo` 表单保存路由。
- 内存持有昵称演示配置；重启后恢复默认值（文档明确声明）。
- 已安装至 `cmd/harness/main.go`。
