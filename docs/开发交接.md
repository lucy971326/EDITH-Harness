## 最近讨论：上下文用量

用户想直接使用模型返回的 token 用量，模型窗口大小由 Harness 配置，不自行精确计数。

已查锁定依赖 **goai v0.9.8** 本地源码：

| 信息 | 当前情况 |
|---|---|
| 模型上下文窗口大小 | goai 没有容量查询接口；Harness 的模型清单也没这个字段 |
| 实际请求用量 | goai 支持，在 `provider.ChunkFinish.Usage` 返回 |
| 发送前 token 预估 | 未发现 goai 内置 tokenizer / CountTokens 接口，Harness 未实现 |

`kernel/llm/client.go` 直接返回 goai 流；`plugins/kernel/loops/react/react.go` 目前只处理文字、推理、工具调用、错误，没有处理 ChunkFinish 的用量。Runner 事件也没有用量字段。

goai Usage 有 InputTokens / OutputTokens / TotalTokens / ReasoningTokens / CacheReadTokens / CacheWriteTokens；各字段是否有实际值依赖供应商响应。

**不要把缓存命中量当成上下文占用。** 当前 goai OpenAI-compatible 层会从 prompt_tokens 中减去 cached_tokens：

```text
最近请求的输入占用 = InputTokens + CacheReadTokens
输入占用比例       = 输入占用 / 配置的上下文窗口
```

这是当前兼容层的语义，新增供应商时要核对其映射。缓存也占上下文。不要把多次请求累计消耗当成上下文占用；这个比例是最近请求的输入占用，不包括之后新增消息，也不是下一次请求的精确预测。

DeepSeek 走共享 OpenAI-compatible 实现，会请求 `stream_options.include_usage=true` 并解析用量。本次只查代码，没调用真实 API；DeepSeek 线上实际返回哪些缓存字段尚未验证，不能保证全部缓存统计准确。

依赖源码位置（Go module cache 下 `github.com/zendev-sh/goai@v0.9.8/`）：

- `provider/types.go`：Usage 约 619 行；ModelCapabilities 约 629 行。
- `internal/openaicompat/openaicompat.go`：请求用量约 65 行；解析映射约 416 行；ChunkFinish 约 617 行。
- `provider/deepseek/deepseek.go`：共享兼容实现约 65 行。

LLM 服务整体边界合理：只做 Models / Stream，不读写账本、不执行工具、不管 Chat。暂不需要 Provider 登记处或重构。小的不一致：Models 只检查供应商配置存在，未检查 key 非空；UI 要求明确思考档位，但 Stream 接受空档位。这些仅记录，未要求修复。

## 压缩：讨论过，尚未定稿或实现

用户曾要求探索 `/compact`，随后转去调查 LLM。不要把下列建议当成已批准方案。

- 账本节点是 ID / Parent / Seq / Message；Session.History 当前返回整条分支消息，Entries 用于完整界面记录。
- UI 分叉实际是复制选定回答之前的历史，创建独立 Session；新节点 ID 会重建。
- 曾建议追加压缩记录：摘要 + 覆盖终点，保留旧节点；History 派生“摘要 + 最近消息”，Entries 仍展示原始历史。
- 若采用节点引用，分叉时必须重映射；保留边界不能拆开工具调用与结果。
- 建议仅空闲时压缩，期间独占会话，生成成功才落账；失败不改变有效上下文。
- `/compact` 是命令入口，但持久压缩和历史投影需要明确归属。Command 系统目前尚未实现，不为此预建通用框架。
