## 1. 项目一句话

edith-harness 是一个 Go 写的静态插件化 Agent 框架：core.App 是公共能力柱，插件围绕它提供能力、领取能力、提供插槽或填充插槽。

~~~text
插件安装到 App
      ↓
App 保存“能力名 → 能力对象”
      ↓
其他插件按能力名领取并协作
~~~

它不是 CRUD 应用。核心是：可替换的模型、工具、执行器、存储和 UI，共同组成一个可以运行、取消、恢复的 Agent。

### App 的真实职责

core.App 不是 Agent，也不懂模型、工具、网页或会话业务。它只做公共组装：

~~~text
App
├─ RegisterService / Resolve    按字符串名字放入、领取能力
├─ Install                      按顺序启动插件，失败时逆序回滚
├─ OnCleanup / Close             注册和执行收摊函数
├─ ForChild / Restrict           创建会话作用域，继承或裁掉能力
├─ Subscribe / Broadcast         发送和接收事件
├─ Intercept / RunChain          运行事件中间件链
└─ RegisterTask / Run...         登记并运行任务
~~~

插件的四种动作：

~~~text
提供能力   app.RegisterService("名字", service)
领取能力   core.Resolve[T](app, "名字") 或包自己的 Get(app)
提供插槽   提供一个带 RegisterX 的 Service
填充插槽   领取这个 Service，再 RegisterX 自己的实现
~~~

能力名使用字符串是当前明确约定，例如：

~~~go
app.RegisterService("agents", service)
agentsService, err := core.Resolve[agents.Service](app, "agents")
~~~

### 3.2 非插件的公共接口包

这些目录定义“别人可以使用的能力或协议”，自己不负责启动：

~~~text
core          插件接口和 App 公共基础设施
chat          消息、ToolCall、用量等公共数据
environment   会话执行环境的 Provider 接口
ui            界面启动入口 Service 接口
workspace     files / process / shell 等执行环境接口
~~~

判断方法：有 Plugin 结构体并实现 Name、Start 的，是安装插件；只定义接口或数据的，是公共协议。

## 4. 当前 App 中的能力和插槽

根 App 的服务表可以理解为一组字符串抽屉：

~~~text
根 App
├─ "settings"      → config.Settings
├─ "credentials"   → config.Credentials
├─ "project-store" → projects.Store
├─ "preset-store"  → presets.Store
├─ "journal"       → session.Journal
├─ "sessions"      → *session.Store
├─ "projects"      → projects.Service
├─ "presets"       → presets.Service
├─ "llm"           → *llm.Service
├─ "tools"         → *tools.Registry
├─ "commands"      → commands.Service
├─ "environment"   → environment.Provider
├─ "agents"        → agents.Service
└─ "ui"            → ui.Service
~~~

其中真正的“登记处”是下面四个：

~~~text
"llm"
└─ *llm.Service
   └─ Register(Adapter)

"tools"
└─ *tools.Registry
   └─ Register(Tool)

"commands"
└─ commands.Service
   └─ Register(Command)

"agents"
└─ agents.Service
   └─ RegisterRunner(Runner)
~~~

所以 deepseek、files、/movie、loop 都不是根 App 的服务名；它们分别是四个插槽里的填充物。

## 5. 启动和插件组装

程序入口是 cmd/edith-harness/main.go：

~~~text
main
  ├─ 读取用户目录 ~/.harness
  ├─ compose.Open()
  ├─ ui.Get(app)
  └─ ui.Run(context.Background())
~~~

compose.Open 做三件事：读取配置、选择插件、按固定顺序安装插件。

当前安装顺序：

~~~text
config
→ project-store / preset-store / journal
→ session
→ llm → deepseek
→ tools → commands → environment → files
→ projects → presets → agents
→ loop
→ ui-web 或 ui-terminal
~~~

启动顺序表达依赖关系：先有登记处，再有填充物；先有领域 Service，再有使用它的 Agent 和 UI。

配置文件只选择已经编译进程序的大零件：

~~~yaml
version: 2

plugins:
  project_store: projectjson
  preset_store: presetjson
  journal: jsonl
  llm_adapters: [deepseek]
  environment: localenv
  tool_plugins: [files]
  runner: loop
  ui: web
~~~

当前是静态编译插件，不做动态加载、热更新或自动依赖排序。

## 6. Project、Preset、Session、Conversation

~~~text
Project
└─ 一个工作目录
   └─ Session
      ├─ 一本独立账本
      ├─ 锁定一个 Preset 版本
      └─ 由 Conversation 负责运行
~~~

### Project

项目对应一个工作目录，有稳定的 ProjectID。项目服务负责创建、读取、归档、恢复和记住该项目最近使用的模式与模型。

### Preset

Preset 是 Agent 模式，不是模型：

~~~text
Preset = SystemPrompt + Tool 白名单 + 不可变 Revision
~~~

创建 Session 时锁定当前 Revision。之后修改 Preset 会产生新 Revision，不影响已经存在的 Session。

### Session

Session 是持久化账本，不是正在运行的 Agent。当前 session.Header 包含：

~~~text
FormatVersion
ID
Title
CreatedAt
ProjectID
ProjectRoot
PresetID
PresetRevision
~~~

Session ID 是内部身份；Title 只是展示标题，允许重复。

session.Store 负责打开、创建、读取、释放账本；session.Session 负责追加事件和从事件计算模型历史。

### Conversation

Conversation 是一段正在运行的会话门面：外部通过它发消息、取消、等待、切换模型、读取账本和关闭会话。

~~~text
agents.Conversation
├─ SessionID / Book
├─ State / WaitIdle
├─ SubmitFollowup   新一轮消息
├─ Steer            当前轮的下一步消息
├─ SelectModel      空闲时切换下一轮模型
├─ Cancel           取消当前工作
└─ Close            停止并释放会话
~~~

agents 管 Conversation 的创建、恢复、查找和关闭；真正执行消息的是 loop。

## 7. 一条消息的运行链

~~~text
Web / 其他调用方
      ↓
agents.OpenSession 或 StartSession
      ↓
Conversation.SubmitFollowup
      ↓
先写 inbox/deliver，再放入 Inbox
      ↓
Driver 被唤醒
      ↓
Turn：处理一条用户消息
      ↓
Step：一次模型请求 + 这次请求触发的 Tool
      ↓
没有 Tool → Turn 结束
有 Tool  → Tool 结果入账 → 再执行一个 Step
~~~

loop 内部的层级只有这几层：

~~~text
Conversation
└─ Driver（一个 goroutine）
   └─ Turn（一条用户消息的一轮完整处理）
      └─ Step（一次模型请求和其 Tool 调用）
~~~

消息入口：

~~~text
SubmitFollowup(text)
└─ next-turn：一定开启新 Turn

Steer(text)
└─ next-step：忙时进入当前 Turn 的下一步；闲时成为新 Turn 的开头
~~~

取消链：

~~~text
Conversation.Cancel()
  → 当前 Step 的 Go context 被取消
  → LLM / Tool 收到取消信号
  → 已收到的流式文字固化为 interrupted 回复
  → Step / Turn 收口
~~~

## 8. 账本是唯一事实来源

账本只追加，不修改旧事件。当前内核事件包括：

~~~text
user/message       用户消息
chunk              模型流式文字
assistant/final    模型完整回复、Thinking、用量、是否中断
tool/call          模型请求调用 Tool
tool/start         Tool 真正开始执行
tool/result        Tool 结果
turn/start/end     Turn 边界
step/start/end     Step 边界
inbox/deliver      消息进入 Inbox
inbox/claim        消息被 Driver 领取
request/snapshot   发给模型的完整请求
summary            压缩摘要
model/selected     会话使用的模型和思考档位
~~~

写入规则：

~~~text
危险操作前 Flush
账本先记事实，再广播观察事件
流式 chunk 可以批量落盘，关键事件立即落盘
工具已开始但没有结果 → unknown，不自动重跑
工具尚未开始 → skipped
~~~

模型历史由 session.Session.ModelHistory() 计算：连续 chunk 折成回复，被 Summary 取代的旧事件不再出现；Turn、Step、Snapshot、ToolStart 等运行事实保留在账本，但不直接变成模型消息。

当前 loop 发给模型的请求由以下内容组成：

~~~text
system prompt（来自已锁定的 Preset）
+ session.ModelHistory()
+ tools.Registry.Schemas(sessionID)
+ 当前 Session 的 Provider / Model / Thinking
~~~

request/snapshot 保存完整请求，因此可以知道某一步实际发给模型看了什么。

## 9. 模型、思考档位和工具

### 模型

~~~text
llm.Service
└─ 多个 Adapter
   └─ 每个 Adapter 自己声明 Provider、Model、ThinkingLevels
~~~

llm.Selection 是一次会话选择：

~~~text
Provider + Model + Thinking
~~~

思考档位属于具体模型，不是全局固定菜单。llm.Service.Validate 会按适配器声明检查组合。

当前 DeepSeek 适配器把选择翻译到官方 SDK：

~~~text
off        → thinking.type = disabled
low/high/max
           → thinking.type = enabled
              reasoning_effort = 对应档位
~~~

适配器还负责把 SDK 的流式文字、Thinking、Tool Call 和 Usage 翻译回统一的 llm.Reply。

### 工具

~~~text
tools.Registry
├─ 全局 Tool 表
└─ 每个 Session 的 Tool 小表
   ├─ 支持同名遮蔽
   └─ 支持 Tool 白名单
~~~

loop 读取当前 Session 能看到的 Tool Schema，把模型返回的 Tool Call 交给 tools.Registry.ExecuteCall；工具生命周期由 tools 记入账本。

### 命令

Command 是人直接调用的 / 命令，不是 Tool：

~~~text
用户输入 /xxx
  → Web 调 commands.Execute
  → commands 解析、查找、执行
  → 返回给人看的 Result
~~~

命令默认不进入模型、不消耗 token、不经过 Tool Pipeline；未知命令返回错误，不降级成普通消息。

## 10. 会话作用域和本地环境

每个 Session 有自己的 core.App 子作用域：

~~~text
根 App
└─ Session 子 App
   ├─ 继承公共能力
   ├─ files
   ├─ process
   └─ shell
~~~

localenv 是环境 Provider。它在会话启动时按 ProjectRoot 挂载 files、process、shell；会话关闭时回收进程树和相关资源。

工具登记在全局 tools，但执行时带 ScopeID，因此不同 Session 的工作目录和工具作用域互不串线。

## 11. Web UI 当前边界

~~~text
浏览器
  ↕ HTTP / HTMX / SSE
uiplugins/web
  ├─ 领取 projects / presets / sessions / agents
  ├─ 领取 llm / tools / commands
  ├─ 渲染页面和片段
  ├─ 转发消息、模型、命令和取消操作
  └─ 监听账本事件刷新页面
~~~

Web UI 不直接依赖 loop，也不执行模型或工具。所有 Agent 工作都通过 agents 完成。

当前页面职责：

~~~text
Project → Session 左侧导航
新草稿 → 首次发送时才创建 Session
聊天页 → 读取账本并显示回复
模型选择 → 使用 llm 的 Provider / Model / Thinking 目录
命令输入 → 以 / 开头时进入 commands 平面
实时刷新 → SSE 只通知，页面按片段更新
~~~

UI 协议接口在 ui/service.go；可运行实现是 uiplugins/web，终端实现目前只是暂停提示。

## 13. 当前代码和未来方向要分开


未来设计集中在：[未来计划.md](../计划书/新阶段计划书/未来计划.md)：

~~~text

2. Settings / Credentials   当前基础版已存在，继续完善插件自包含配置
~~~

未来方向不能直接当成当前代码。开始实现前，先说明：这次是在使用已有能力、填充已有插槽，还是要新增一个真正的插件能力。


建议工作顺序：

~~~text
1. 先读本文和 AGENTS.md
2. 用 CodeGraph 建立模块和调用关系
3. 按“当前事实 → 设计判断 → 可选改动”输出观察

~~~


## 15. 验证和提交约定

代码改动后按范围运行：

~~~bash
go test -race ./...
go vet ./...
git diff --check
~~~

不自动提交。用户明确说“提交”后再提交。Commit 使用双语格式：

~~~text
中文摘要（50 字内）

English body: what changed, why, and how it was verified.
~~~

当前 UI 架构图在 docs/AGent对接/harness-live-map.html；真实模块或能力关系发生变化时同步维护。
