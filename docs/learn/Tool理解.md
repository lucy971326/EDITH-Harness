# Tool：平台能力的受控入口

面试时可以这样讲：

> 我们的 Tool 不只是把一条命令丢给操作系统执行一下。它是 Agent 调用真实机器能力的受控入口。
>
> 最关键的是，我们把“调用 Tool”与“进程生命周期”分开了。LLM 调 `exec_command` 时，Tool 负责校验参数、权限和工作区，然后交给 Machine 启动进程。
>
> 如果这是一个带 PTY 的长期进程，例如开发服务器或交互式 Bash，Machine 会把它保存在自己的内存进程表里，分配一个 `process_id`，并记录它属于哪个 Session。Tool 只把这个 `process_id` 回传给 Agent。
>
> 后面 Agent 再调用 `write_stdin`，带着同一个 `process_id`，Machine 就能找到原来的 PTY，把新输入写进去，并返回这段时间新增的输出。
>
> 所以 Tool 是协议和安全边界，Machine 才是资源所有者：它真正持有进程、PTY 和输出缓冲，也负责取消时杀掉进程树。这样模型可以多轮使用同一个终端，但不能越过 Session 去碰别人的进程。

一句话收尾：

> Tool 是 Agent 使用平台能力的统一协议层；Machine 是长期进程和真实机器资源的所有者。

## Tool 平台化后，Agent 发生了什么变化

> 把 Tool 从散落函数提升为平台能力入口，意味着 Agent 不再只是调用 API 的语言模型，而是平台里的受控执行单元。它能跨多轮推进真实工作，但状态、权限、生命周期和审计都由平台接管。

可以展开为三点：

1. **从单个动作变成持续工作。** Agent 不只会启动 `npm run dev`，还可以在后续轮次读取同一进程的日志、继续输入命令或停止它。

2. **从返回文本变成返回资源回执。** Tool 可以返回 `process_id`、子任务 ID 或文件 Delta。Agent 拿着回执继续操作同一个平台对象，而不是依赖模型记忆。

3. **从直接操作变成受控使用。** Agent 只能发 Tool Call；Machine、Subagents 和 Runner 分别持有真实资源、协作关系与本轮变更。平台负责校验归属、管理取消和保留审计记录。
