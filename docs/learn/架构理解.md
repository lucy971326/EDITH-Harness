# 进程装配：整个项目怎么拼起来

一句总纲：

> 进程是一张服务表。聊天是桌上的一个产品，不是根。

厨房怎么炒菜（Session / Runner / Tool / Machine）已经另有理解稿。这篇只讲：**进程怎么装配，门卫怎么接入，新产品怎么接进来。**

---

## 1. 总图

```text
Web / 未来 Wails / 测试 Client
        │  手写 TS 契约
        │  WebSocket + JSON-RPC 2.0
        ▼
   一个 appserver          ← Host 外，入口创建和关闭
        ├─ HarnessProduct  聊天业务：开桌、发送、Steer、停止、分叉
        └─ 公共服务         agents / skills / commands / models / 文件 / 终端
                │  进程内 Go 调用
                ▼
           Host 服务表
           ├─ 整份服务    persist / sessions / llm / machine / agents / runner / harnessProduct
           └─ 登记处      tools / loops / skills / commands / events
```

多 Client 连的是**同一个** appserver，背后是**同一张** Host 服务表。没有每个窗口一套后台。

---

## 2. appserver：门卫，不是店

appserver 在 Host 外面。入口 `cmd/harness` 创建它、Bind 方法、最后才 Listen。它不登记进服务表，也不读取 Host。

```text
一个浏览器窗口  =  一条 Connection
```

Connection 只干接入的事：协议初始化、RPC、订阅、断线清理。它不存 Session、Run、设置，也不决定 Start / Steer / Stop。

所以：

- 两个 Client 同时在线，共享同一份 Product 和公共服务。
- 某个窗口关掉，只拆这条连接的监听；已经接受的 Run 继续跑。
- Host 上有什么，不会自动变成网络方法。只有 `BindHarness`、`BindAgents` 这些显式登记的才能调用。

HTTP 只送静态页面。业务一律走 WebSocket + JSON-RPC。

---

## 3. Product 和公共服务：别让聊天吞掉平台

appserver 后面分成两条，不是什么都进 HarnessProduct：

```text
聊天编排     → HarnessProduct
公共能力     → 直接调对应服务
              模型列表、Agent 设置、Skill 目录、
              斜杠命令、文件、浏览器终端
```

模型、Agent、Skill、命令这些，appserver 自己 Bind，不经 Product 做搬运工。

以后要加**第二个后台产品**（下面第 6 节，v1 没做）：

```text
业务放自己的 Product
状态放自己的 Store
Runner / Session / LLM / Tools / Machine 继续复用
appserver 增加对应接口文件并 Bind
```

不给新产品再造一个小 Host，也不让产品插件自动往网上挂方法。

---

## 4. Host 三种挂法

先分清三个词：

```text
服务        挂在 Host 表上的值
插槽条目    登记处里面的一项（某个 Tool、某个 Loop、某条命令）
活对象      运行后才有的东西（某一桌 Session、某一盘 Run）
```

插件不管业务实现，只负责组装：`Name + Start + Close`。Start 时解析依赖、构造、挂表或填表。

### 4.1 注册整份服务

不能拆着换的，整份挂上。别人 `Resolve` 出来直接用。

```text
RegisterService("llm", client)
RegisterService("runner", runner)
RegisterService("harnessProduct", product)
```

现在这类有：`persist`、`sessions`、`llm`、`machine`、`agents`、`runner`、`harnessProduct`。

### 4.2 注册登记处

能换、等人来填的，先挂一张空表。

```text
RegisterService("tools", registry)
RegisterService("loops", registry)
RegisterService("skills", registry)
RegisterService("commands", registry)
RegisterService("events", registry)
```

此时表上有登记处，里面还没有条目。

### 4.3 填登记处

后面的插件再 `Resolve` 到那张表，往里 `Register` 或 `RegisterProvider`：

```text
exec / apply_patch / subagent tools   → tools.Register
MCP                                   → tools.RegisterProvider
react                                 → loops.Register
builtin / filesystem skills           → skills.Register
compact                               → commands.Register
```

MCP 仍是填 `tools` 这张表，只是填的是动态来源，不是第四种挂法。

启动顺序只写在 `cmd/harness`。用户配置不能发明还没编译的插件，也不能重排。中途失败：已 Start 的倒序 Close。正常退出：先关 appserver（拒绝新调用、断开连接），再关 Host。

### 4.4 为什么要这样

契约写在定义者包里。提供者和消费者都 import 定义者，**彼此不 import**。

```text
internal/tools 写出 Tools 契约
internal/tools/exec 实现并填进去
internal/runner 按契约调用
exec 和 runner 互不认识
```

若不走登记处，就会变成：

```text
runner import exec
product import runner 又 import 某个 tool
某个 plugin 再 import product
```

依赖织成网，换一个 Tool、加一个 Loop，到处改 import。Host 运行时只存服务；类型安全来自 Go 包里的契约，不是来自一张字符串表的幻想。

能独立替换、或确实需要别人填充，才做登记处。默认整份服务、直接方法。不为测试或假想未来预建抽象。

---

## 5. 假想：再接一个后台产品

v1 只有 `HarnessProduct`。下面不是已实现功能，只说明扩展落在哪。

假如要接第二个后台产品：

```text
1. products/foo 写自己的业务和 Store
2. 插件 Start 时 Resolve 已有 runner / sessions / llm / tools
3. RegisterService("fooProduct", foo)
4. appserver 增加 foo 的接口文件，入口 BindFoo
5. 多个 Client 仍然连同一个 appserver
```

新产品共用厨房和平台能力，不复制 Session / Runner / Machine。页面组件不是后台插件契约。

---

## 6. 面试口语稿

### 主稿（约 90 秒）

> 我们这个项目的根不是聊天，而是一个本机宿主进程。进程里是一张服务表，聊天只是挂在上面的一个产品。
>
> 多个 Client，比如 Web、以后的 Wails、测试 Client，都连同一个 appserver。协议是 WebSocket 加 JSON-RPC。appserver 在 Host 外面，只做接入、校验、订阅和断线清理。一条 Client 对应一条 Connection，它不保存 Session 或 Run。窗口关了，已经接受的运行不会跟着停。Host 上的服务也不会自动暴露成 RPC，必须显式 Bind。
>
> appserver 后面分成两路。聊天的创建、发送、停止走 HarnessProduct；模型、Agent、Skill、命令、文件这些公共服务，直接调对应模块，不经产品转发。所以以后加第二个产品，是新增自己的 Product 和接口文件，复用现有 Runner、Session、LLM、Tools，而不是再造一套内核，也不是再造一个小 Host。
>
> 内核用注册和拿取来组装。有的是整份服务，Resolve 后直接用，比如 LLM、Runner、Product。有的先注册空登记处，比如 tools、loops、commands，再由别的插件把具体 Tool、Loop、命令填进去。契约由定义者写，提供者和消费者都依赖定义者，彼此不依赖。这样就不会织成网状 import。插件只负责 Start 和 Close，启动顺序固定写在入口。

### 追问 1：为什么 appserver 不进 Host？

> appserver 是进程边界上的门卫，不是给别的插件 Resolve 的业务服务。它由入口创建和关闭，直接持有 Product 和公共服务。放进 Host 会让内核反过来依赖接入层，Bound 也会被搞成“谁都能拿网关”。Connection 更不能进服务表：它是瞬时连接状态，断线即失效。

### 追问 2：三种挂法怎么讲？

> 表上的值都叫服务。一种是整份服务，挂上去就能用。一种是登记处，先挂空表。第三步是填表：别的插件 Resolve 到登记处，再 Register 条目。MCP 的 RegisterProvider 也是填 tools 表，不是第四种模式。运行中的 Session、Run 不挂在这张表上，它们是活对象。

### 追问 3：这怎么防止依赖网？

> 如果 exec 插件直接被 Runner import，MCP 再被 Product import，新产品又去 import 某个 Tool，依赖会交叉。我们让 kernel 只出契约，plugins 只填充，products 只消费契约。大家共同依赖定义者，不互相依赖。换实现时改插件，不改调用方。

### 追问 4：新产品怎么接？

> 业务放新 Product，状态放新 Store，执行仍用现有 Runner 和 Session。入口把产品 Resolve 出来，appserver 加 Bind 文件。不自动扫描插件挂 RPC，也不给产品自己搭一个 Host。v1 还没有第二个产品，但这条接法是现在就留好的。
