# Subagent 系统实施计划：分 6 步完成

## 一、目标与已确定规则

实现“父任务异步派出孩子、追加要求、等待结果、停止父子”，复用现有 Runner，不另建运行器。

```text
父 Run
  |
  +-- 工具 --> 子会话委派服务 --> Runner --> 子 Run
  |                |
  +<-- 完成通知 ---+
       工作中：检查点接收
       等待中：结束等待，继续同轮
       已结束：保存通知，不自动开新轮
```

已拍板：

- 第一版只做后端和工具，不做子任务面板。
- 只允许一层委派；不设孩子数量或并发上限，不自动排队。
- 孩子新建独立 Session，不复制父历史，只接收委派说明。
- Agent、模型、思考档位可指定；未指定时继承父 Run 的配置快照。工作区始终继承。
- 父给孩子追加要求：忙时 Steer，闲时新 Run，复用子 Session。
- 等待保留父 Run，但不保持模型请求；用户插话可以提前结束等待。
- 用户停止父会话时父子都停；正常回答结束不等于停止孩子。
- 重启只恢复记录，未完成运行标记中断，不自动执行。

### 服务名称与工具边界

子会话委派服务（代码包与 Host 键保留 `subagents`）：管理父子 Session 关系、委派状态与完成通知，通过 Runner 启动和停止子 Run。委派服务决定启动谁、通知谁；Runner 负责实际运行和收尾。

```text
统一 Tools Registry
  +-- WorkspaceTools   内置工作区工具：read / write / edit / bash
  +-- PlatformTools    内置平台工具：委派、追加要求、等待、停止等
  +-- ExternalTools    外部扩展工具
        +-- MCP 接入
        +-- 未来通过 SDK 扩展
```

- 三类沿用同一种 Function Call、工具登记处分发、权限检查和结果落账；PlatformTools 不是第二套 Registry，也不是新的 Runner。
- ExternalTools 表达外部扩展来源，不限定远程服务，也可操作本地资源；分类不授予权限。
- 首版分类仅作职责说明，不增加分类接口、字段、子登记处或目录重构。SDK 只保留方向，不提前搭框架；Go 扩展仍静态编译，不动态加载。
- Tools Registry 不大改：本次只补可信调用身份和注册平台工具，主要实现位于委派服务与 Runner 的协作边界。

## 二、分步实施

### 第 1 步：补齐 Runner 的可靠运行接口

**产物：可信调用身份、可观察的异步完成结果。**

- Runner 启动成功时返回运行句柄，包含稳定 RunID、完成信号和最终状态；Chat 等调用方同步适配，不保留两套启动实现。
- 完成信号必须覆盖成功、取消、早期落账失败和事件发布失败；释放当前 Session 的运行占用后，再宣布完成。
- 取消或关闭后不得重新开放插话；Runner 关闭返回前，已启动 Run 的句柄必须已完成，后台处理已经退出。
- `Invocation → tools.Call` 传递 SessionID、RunID、ToolCallID，全部由程序提供，不进入模型参数。
- 提供按 SessionID、RunID 获取本轮配置快照的接口，供继承设置使用；不重新读取可能已经修改的父设置。
- 提供输入到达信号，让阻塞中的等待工具能响应 Steer；信号只负责唤醒，消息仍由检查点消费。

第 1 步接口细则：最终结果只带运行身份、状态与错误，正文后续读取账本；运行期间可按 SessionID、RunID 查询配置快照，句柄可保留快照，但 Runner 不缓存已结束运行。Chat 对 Web 仍返回 error，不保存无用途句柄。ToolCallID 沿用协议调用 ID，由 Loop 传入，不从 Arguments 取身份，不另造 ID 映射。尚未尝试发布运行开始时不强造 RunEnded；一旦尝试发布开始，即使部分订阅失败，也尝试结束通知并保留错误，早期失败始终由句柄可靠返回。输入信号需传至 tools.Call；只要 Steer 尚未被检查点消费，多个或后开始的等待都能观察到，停止由取消 Context 区分。初始化阶段必须保证首条输入在先、Steer 不重复进入初始历史和检查点；Compact 从注册运行占用时就拒绝 Steer。

**验收：** 极快完成也能获取结果；早期失败不漏报；停止不会被启动竞态覆盖；原有聊天、Steer、工具取消测试通过。

### 第 2 步：建立子会话委派服务及独立存储

**产物：一份管理父子关系与协作状态的服务。**

- 新增 `kernel/subagents`，Host 键为 `subagents`，是整份服务，不是登记处。
- 使用 Runner、Session、SessionSettings、Agent 与 LLM 服务；不直接执行 Loop，不直接写对话账本。
- 服务提供 `Options / Spawn / Send / List / Wait / Stop / StopFamily`。
- 任务 ID 长期稳定；同一孩子每轮另记 RunID 和递增轮次，避免旧结果覆盖新一轮。
- 保存父子 Session 关系、运行状态、结果位置、错误与待投递通知。业务数据放在 `~/.harness/subagents/`，不混入 SessionSettings。
- 使用版本化 JSON 和原子替换保存；持久化失败明确返回错误，不能报告任务已可靠保存。
- 创建时先保存任务关系，再创建子 Session 和设置，最后启动。失败留下明确失败状态；重启将未完成创建或运行标记中断。
- 子 Session 不进入普通聊天列表，也不能被“复用空会话”逻辑选中；由 Subagents 查询其记录。

**验收：** 重启仍能查询任务和历史；旧轮次不能覆盖新状态；创建失败不会留下可被普通聊天误用的孩子。

### 第 3 步：实现委派、追加要求与工具入口

**产物：模型可调用的薄工具插件。**

| 工具 | 行为 |
|---|---|
| `subagent_options` | 查询已有 Agent 的 ID、名称、用途，以及模型和各自支持的档位 |
| `subagent_spawn` | 输入委派说明及可选设置，立即返回任务 ID、子 SessionID 和 RunID |
| `subagent_send` | 向指定孩子追加文字要求，返回接收情况及所属轮次 |
| `subagent_list` | 查询自己的孩子、状态与已保存结果；可指定任务 ID |
| `subagent_wait` | 等待指定孩子出现新完成结果，或查询当前状态 |
| `subagent_stop` | 停止指定孩子，不停止父 |

具体规则：

- 模型清单直接使用 `llm.Models()`，Agent 清单使用现有 Agent 服务，不维护第二份名单。
- 每个可选设置独立继承；覆盖模型后，若继承的档位不兼容，明确报错，不偷偷换档位。
- `send` 第一版只追加要求，不修改孩子设置。
- 服务校验调用者确实拥有目标孩子；孩子即使配置了 spawn 工具，也不能继续委派。
- 忙闲切换必须原子判定：只有明确“尚未接收”的输入才能转为启动新 Run，不能因错误盲目重发。
- 工具沿用普通 Tool 的启用规则；不暗中给已有 Agent 勾选新工具。
- 父子共用工作区；不自动建立 worktree，也不新增文件写入隔离。

**验收：** 设置继承和覆盖正确；未知模型、档位、Agent 明确报错；越权和递归委派被拒绝；追加要求不重复执行。

### 第 4 步：实现完成通知与同轮等待

**产物：结果可靠保存，父任务在正确时机接收。**

- 子 Run 完成后，先保存状态与结果位置，再生成通知；结果取该轮最终助手正文，失败或取消明确标注，不能把中途文字当成功答案。
- 每条协作消息有稳定消息 ID、来源 SessionID 和 RunID；Runner 按消息 ID 去重落账。
- 协作输入增加明确来源标记，不能冒充用户或提升成系统指令；发给模型时按带来源说明的普通输入处理。
- 父运行中：通过 Runner 接收，在检查点交给 Loop；若最终检查点已关闭，则保留待投递。
- 父已经结束：仅保存通知；下一次用户主动启动父会话时，在首次模型请求前接收。
- `wait` 等待任一指定孩子的新完成结果；默认 60 秒，允许 0～60 秒，0 表示立即查询。
- 超时不停止孩子；用户 Steer 提前结束等待；用户 Stop 取消等待并执行父子停止。
- `wait` 返回状态、轮次与通知 ID，结果正文通过同一通知路径交付，避免自动重复注入两遍。
- 去重确认以账本中实际存在的消息 ID 为准；通知确认写盘失败后重试，不重复写消息。

**验收：** 先完成后等待、多个孩子同时完成、最终检查点附近完成、用户插话和重复投递均正确；等待期间没有持续模型请求。

### 第 5 步：接入父子停止与启动关闭流程

**产物：停止与关闭后不会误启动任务。**

- ChatService 的用户停止入口调用 `StopFamily`；Subagents 再调用 Runner 取消父和孩子。
- 停止先禁止本次协作继续派生或唤醒，再发出取消；与并发 spawn、send、完成通知互斥协调。
- 父已闲置但孩子仍运行时，停止父会话仍能停止这些孩子。
- 单独停止孩子保留任务及历史；之后父明确 `send` 可以开启新一轮。
- 取消后已落账工具调用仍按现有规则补齐结果，不执行剩余工具。
- 启动顺序固定为 Runner → Subagents → ChatService；工具在 Subagents 可用后注册。
- Subagents 关闭时拒绝新请求、解除等待、取消其孩子并等待自身后台处理退出；之后再关闭 Runner。
- 重启保留待投递通知，但没有任何自动恢复执行或自动唤醒。

**验收：** stop 与 spawn/send/完成同时发生时不漏停、不复活；Host 关闭不死锁、不泄漏后台任务。

### 第 6 步：集成验收与文档收尾

**产物：可实际使用、可交接的首版。**

- 自动化覆盖：两个孩子并行、不同模型配置、多次交流、等待插话、父子停止、失败结果、持久化失败与重启。
- 执行 `go test ./...`、`go vet ./...`、相关运行与协作包的 `go test -race`、`git diff --check`。
- 真实模型验收：父派两个孩子，向其中一个追加要求，等待后汇总；另起一次验证父子停止。
- 沿用现有工具结果展示；不新增 SSE 事件类型、专用界面或 JavaScript。
- 更新 AGENTS、设计书及 DATA_MODEL 中过时的 Subagent 边界说明；完成事实写入 STATUS，删除已完成计划及后续计划入口。

## 三、交给 Subagent 的执行方式

采用 **Luna Max Fast**，按第 1～6 步顺序实施，不把紧密相关的 Runner、通知、停止逻辑分给多个 Agent 同时修改。

每一步必须交付：

1. 本步代码和对应测试。
2. 实际运行的验证命令及结果。
3. 公共接口变化、已知未完成项。

首次派发只允许只读检查并复述任务、范围、方案和验收条件；主 Agent 确认理解无误后，才明确授权实现第 1 步。有误先纠正，再开始。

禁止执行者派出任何 subagent。实现与测试尽量由同一个 Luna Max Fast 执行，主 Agent 负责审查，不重复运行无必要的测试、不催促执行者。

每步实现并测试后，由主 Agent 审查；有问题交回修正，无问题即停下向用户报告，等待用户要求后再进入下一步。本次仅授权第 1 步，不自动推进第 2 步。重点审查第 1、4、5 步。若发现计划与代码事实冲突，先报告证据，不自行扩大范围、增加通用调度系统或改动已拍板行为。
