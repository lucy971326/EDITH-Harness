## 1. 根是宿主

进程是一张服务表。聊天是桌上的一摊，不是根。

```text
Host
  整份 A     persist（三把键） / sessions / sessionSettings / agentStore
             llm / machine / agents / runner / harnessProduct
  登记处 B   tools / loops / skills / commands / events
```

能换的做成登记处，等人来填。不能换的做成一整份服务。新增产品在 appserver 显式接入，不建立旧页面登记处或产品自己的 Host。狼人杀、多机器人是验架构的例子，v1 不做。

`RegisterService` / `Resolve`。定义者出契约，提供者装上，消费者 import 定义者，彼此不 import。Host 不叫 `App`。

启动顺序写在 `cmd/harness`，yaml 只选这次启不启动，不能发明还没编译的插件，也不能改顺序。内核每次都 Start，不进 `enable`。persist 包一次挂 `sessionPersistence`、`sessionSettings`、`agentStore`；jsonl / sqlite 是包内选文件。machine 按 yaml 必装一个提供者。v1 改配置后重启。

动手前先问：这是桌上新的一摊，还是聊天里的一份数据、一种画法？工作区、轨迹页、自定义模式都是聊天产品，不改内核形状。

### 后台接入与产品

```text
React / Web / Wails / 其他 Client
               ↓ 类型化 Client 方法
       WebSocket + JSON-RPC 2.0
               ↓
           app-server
        ┌──────┴────────┐
        ↓               ↓
HarnessProduct      公共服务接口
        └──────┬────────┘
               ↓ 进程内 Go 调用
              kernel
```

`appserver/` 是独立顶层包：入口只创建一个 `Server`，它同时拥有方法表、WebSocket 监听和关闭生命周期，不再包装成两个 Server。它位于 Host 外，不登记进服务表，由入口创建和关闭；Server 直接持有 Product 与所需公共服务。`products/harness` 的插件只安装 `harnessProduct`；原 `kernel/chat` 已整体迁移，不保留兼容转发层。

`sourcegraph/jsonrpc2` 负责 JSON-RPC 封套与请求配对，`Server` 中的一张私有 map 负责类型化方法登记、校验和调用。WebSocket 接入负责网络收发，业务仍是进程内调用；通知没有响应，运行事件可主动推送，未来反向请求也复用协议库的请求配对，不另造协议层。

网络参数、结果与接口处理放在 appserver；Product 只保留业务数据和直接方法，不依赖 appserver。入口取出 Product 和事件来源后调用 `server.BindHarness(product, events)`，方法清单留在 appserver。新增产品时增加对应接口文件，不再要求产品插件自动登记网络接口。

Go 类型和方法声明由服务端维护，TypeScript 契约在 `clients/contracts/` 手工维护，各 Client 共用。修改接口时同步两端的方法名、字段、可选性与结果类型，不保留 Go → TS 自动生成链。服务端登记时从 Go 类型生成并编译运行时 Schema，失败则组装失败；登记的方法可直接调用，输入输出仍接受校验。TS 检查不证明两端一致，需在接口变更时对照审查。

入口拥有 app-server 生命周期，Host 只拥有已安装插件。全部安装成功后启动网络监听；安装失败不启动监听，并关闭清理。正常退出先关闭 appserver Server，拒绝新调用、断开连接并解除订阅，等待处理退出后再倒序关闭产品与内核。已接受的 Run 独立于连接取消，由 Runner 的 Stop / Close 收尾。

协议使用标准 JSON-RPC 2.0，保留 `jsonrpc` 字段，支持请求/响应、通知和服务端反向请求。请求 ID 只配对本次响应，不是业务防重 ID；有副作用的调用未经业务操作 ID 保护时不得自动重试。

HTTP 只提供 React + TypeScript + Vite 的静态资源。WebSocket 承载业务调用与事件；Wails 首版复用同一套界面和 WebSocket，不另建 IPC 业务协议。后台内部始终直接调用 Go。

### 本机通信约定

```text
Server            方法表 / WebSocket 监听 / 服务关闭
       ↓
Connection        初始化 / 订阅 / 断线收尾
       ↕
jsonrpc2.Conn     封套 / 请求 ID / 响应 / 通知
       ↓
具名 handler      类型校验 → 产品业务 → 类型化输出
```

- `github.com/sourcegraph/jsonrpc2` 是 JSON-RPC 协议黑盒；现有 `coder/websocket` 继续负责 WebSocket。两者之间只有一个消息流适配，不再自行维护封套解析、请求 ID 配对或通知编码，也不在库外补回未被正式 Client 使用的协议边角。
- 一条 Client 连接只有一个 Harness `Connection`。它是 IM 网关式的基础设施对象，只拥有初始化、RPC 连接、订阅、慢连接保护和断线清理；不拥有 Session、Run、设置或产品状态，不校验业务归属，也不决定 Start、Steer、Stop 或其他业务流程。业务判断只能进入 Product 或对应公共服务。
- `Connection` 断开只解除该 Client 的监听并释放网络资源，不停止已接受的 Run。JSON-RPC 库和 Product 不直接操作底层 WebSocket。
- `Product.Send(ctx, RunInput)` 拥有发送锁、业务校验与忙闲判断，返回 started / steered；appserver 只转换文字请求、调用并映射错误。Start / Steer 保留独立调用边界，旧 Web 沿用原入口。
- WebSocket 一条文本消息是一份 JSON-RPC 消息；正式 Client 只使用单请求、响应和通知，不发送 Batch。畸形封套与 Batch 采用协议库行为，不作为 Harness 自定义兼容契约。产品输入使用命名参数对象，不采用位置参数。
- 连接必须先调用 `initialize({protocolVersion: 1})`，返回 `{protocolVersion: 1}`。版本是 Harness 接入约定版本，封套始终是 `jsonrpc: "2.0"`。Client 按手写契约调用，不动态查询接口目录；Schema 只用于服务端校验。协议内建方法不混进业务登记表，也不允许产品占用它们的名字。
- 本机模式只监听数字回环地址并拒绝跨 Origin 浏览器握手，不增加临时鉴权；初始化超时会断开。未来若支持远程连接，再设计正式身份认证。
- `harness/session/send` 不带身份前提时沿用闲时 Start／忙时 Steer；可选 `expectedRunID` 必须非空，只允许插入该轮，结束／关闭插话／换轮返回 `-32009`，绝不退回 Start。身份检查与插话准入、落账由 Runner 在同一临界区完成。忙时忽略下一轮模型设置，不创建队列。返回 `mode: started / steered` 仅表示输入已接受，不表示运行完成；完整结果走订阅和 Snapshot。
- `model/list({})` 返回 `{models}`；入口取出公共 `*llm.Client`，通过 `server.BindModels` 显式接入，具名 handler 直接调用 `Models()`，不查 Host、不经 Product、不请求模型。`ModelChoice` 的公开 JSON 字段统一为 `id / contextWindow / vision / reasoningEfforts`，不包含 Provider 配置或密钥；Go / TS 手工同步。
- `harness/session/subscribe({sessionID})` 返回 `{subscriptionID, snapshot}`。先装事件监听，再读快照，响应入发送队列后才释放缓冲通知。通知为 `harness/run/event`，参数是 `{subscriptionID, event}`，事件复用 Runner 的稳定数据。
- 生成开始时分配 Entry.ID；增量、草稿和最终落账使用同一 ID。定位为 SessionID → RunID → EntryID → BlockSeq。更新序号只过滤快照边界，不充当消息身份。
- Snapshot 含账本、各轮运行状态、未落账草稿副本、`updateSeq` 与进程 `seqEpoch`。Client 采用快照后只应用序号更大的更新；耐久消息仍按 Entry.ID 去重。
- `updateSeq` 与对应状态一起提交；内核同步事件允许回调重入，不保证回调到达顺序。appserver 的运行订阅以快照为起点，按连续序号放行通知；乱序缓冲有界，超限断线重取快照，不在 Connection 中保存业务状态，也不持 Runner 锁执行监听回调。
- 快照固定运行身份，并与运行记录写入互斥，不能用旧 running 覆盖正常结束。插话的检查、落账与接收共同互斥于最终检查点；已开始的草稿保留原锚点，消费新输入后开始的输出使用新锚点。
- 快照与通知允许重叠。结束事实必须在结束通知发出前对 Snapshot 可见，但仍保留 live 占用到完整收尾，不能提前放行新 Run。重连不要求补齐旧文字 Delta。
- `server/unsubscribe({subscriptionID})` 幂等解除本连接的订阅；断线解除所有监听，不停止 Run。单消息、事件通知队列和订阅缓冲都有上限；超限断线后重新同步，不反压 Runner。
- 合法请求的未知方法、参数和内部错误使用 `-32601 / -32602 / -32603`；初始化拒绝用 `-32001`，重复初始化用 `-32002`，未找到用 `-32004`，冲突用 `-32009`。畸形封套采用协议库行为，可能直接断开。业务错误的 `data` 可带稳定分类，内部 Cause 不发给 Client。

反向请求、业务操作防重和正式多 Client 协调属于后续迁移，不把测试 Client 当正式 SDK。

## 2. 一轮对话

```text
闲着再问     HarnessProduct.Start → Runner.Start → agents.Prepare → 用户消息落账 → Loop.Run →（LLM 类）llm.Stream
跑着插一句   HarnessProduct.Steer → Runner.Steer：立刻落账，Loop 在检查点取走
停止         HarnessProduct.Stop → Subagents.StopFamily → Runner.StopRun：取消父与孩子并收尾
压缩         Runner.Compact：占空闲 live，不是 Loop，不换 Kind
平台命令     commands.Call：按名调用，不经 Agent
```

不要 `Chat.Followup`，不要 Inbox，不要等待队列。`Run(sessionID)`，不加 `appName` / `user_id`。用户拦在 HTTP。

Loop 是一种程序，要编译。登记 Kind 的条件：`Run` 必须取尽 Steer。Loop 启动时自己 Resolve 依赖；`Run` 不碰 Host、Session、Runner。Invocation 只带本轮数据。

活着的 Run 只在 `Runner.live`。同一 Session 同时只能占一次：Start / Compact 互斥。账本只有 Runner 能写。Client 通过 app-server 订阅本轮运行投影，不把账本当实时事件流。耐久事件先 `Append` 再发布，失败则终止 Run。

`Runner.Start` 返回运行句柄，提供稳定 RunID、本轮配置快照、完成信号与最终状态/错误；Chat 对 Web 仍只返回启动错误。先释放 live，再完成句柄，关闭 Runner 会等待后台收尾。运行中的配置查询按 SessionID、RunID 匹配快照，不重新读可变设置，不缓存已结束运行。

Start / Run / Compact 在读取设置与准备 Agent 前就登记 live，停止和关闭覆盖准备期；准备完成前不提供半成品快照。`StopRun(sessionID, runID)` 只取消匹配身份的运行，不误停下一轮。开始事件后、进入 Loop 前再次检查取消。

Steer 的输入信号只唤醒、不消费消息；待处理输入持续可观察，检查点取走后才换信号代次。ReAct 每次工具调用获取当前信号，随可信 SessionID、RunID 与协议 ToolCallID 传入 tools.Call，不从 Arguments 取身份。初始化不能重复消费 Steer；Compact、已取消或正在关闭的运行不接收 Steer。

`Runner.Receive` 接收带稳定消息 ID 和来源的协作消息，与 Steer 共用检查点和输入广播，按实际父账本去重。启动事件期间接收的消息由 Runner 放入初始 History，进入 Loop 前只消费一次。协作输入先落账再发布现有 Message 事件；落账或发布失败终止本轮，并保留真实错误。运行收尾等待在途协作消息发布结束。

`events` 只通知、不存、不代替有返回值的调用。`RunEvent` 只由 Runner 发布；Loop 内部事件不露出表面。换 Loop 不能迫使 UI 改事件名。

## 3. 谁管什么

```text
Agent            Kind / 人设 / 普通 Tool 勾选（设置页默认折在「高级配置」）
SessionSettings  AgentID / 模型 / 思考档位 / 工作区
Skills           系统 + 个人 + 当前项目，自动可用，不写进 Agent
MCP              个人全局自动加入，项目只在当前工作区自动加入；Agent 不选 Server，也不选小工具
```

`agents.Prepare` 现取 Agent、当前作用域 Skills 摘要、已启用 MCP 说明和工作区，拼成最终 System Prompt。Runner 只拿成品。`Prepare` 与 `/`、`$` 候选共用 `AvailableSkills(workspace)`。

没有 `prompts` 登记处。Skills 正文仍在各目录的 `SKILL.md`，不强制加载，不暗中补开 `read` / `bash`；提示词不得宣称未启用的工具可调用。项目 Skill / 项目 MCP 换工作区才换，不串别的项目。MCP 按现有加载时机生效，改配置重启，不热加载。

Agent 和 SessionSettings 都是实时事实；Runner 每轮读一次，改动影响下一轮，不打断当前 Run。Steer 不改 Agent。`default` Agent 可编辑、不可删除；首次生成时勾上当时全部普通 Tool，之后新增普通 Tool 要人勾。

模型键和思考档位键来自 `kernel/llm/models.json`；API key 在 `~/.harness/config.yaml`。两项都是独立选择，首次发送前必选。`off` 是明确选择，空值是还没选。

## 4. 账本

Session **只记对话**，可以分叉。todo、审批、棋盘、Dock、面板宽度都不进账本。

```text
Entries()   完整账本；聊天区画这份
History()   发给模型。若有 summary，从最近一条摘要起：摘要收成普通文本，其后原样保留
```

块：`text` / `reasoning` / `tool-call` / `tool-result` / `image` / `summary`。字级 Delta 不落盘，只留在 Runner 草稿里；完整消息成功落账后才去掉同 ID 草稿。进程崩了只丢尚未 Append 的半截。停止或模型报错时保存已产生的正文／思考并标 incomplete，不能冒充最终回答。

压缩不是新 Loop。成功条件：正常结束且正文非空，才追加 `Kind=summary`。摘要指令只在内存里，不进账本，为的是保住模型前缀缓存。用户必须仍能看见压缩前的对话。

本轮 System Prompt、时长、token **不写进账本**。用量球听 `usage` 事件，刷新后从 0 开始。

`SessionMeta` 只有 `ID / Title / CreatedAt`。新会话标题「新对话」，首条用户消息落账后自动命名。标题不是消息，不进 `SessionSettings`。

项目 = 按 Workspace 分组的 Session，不是独立数据。

## 5. llm / machine / tools

`llm` 直接调 goai，不自写各家协议。`models.json` 手写 `contextWindow`、`vision`、思考档位的 ProviderOptions。不看图的模型：发给它的 image 块换成文字占位，账本和屏幕仍留原图。

`machine` 是一台机器一把键，不要拆成 shell / fs / subprocess。契约在 `kernel/machine`，提供者挂上之后表上才有这把键。`Run` 只执行 argv；bash Tool 自己变成 `bash -c`。工作区是 SessionSettings 里从哪开始，不是另一种机器。不限制路径。

`tools` 是登记处。v1 普通 Tool：`read` / `write` / `edit` / `bash`，都走 machine。不做 grep / find / ls。权限看 `Allow`，不靠 schema 名单。MCP 转成普通 Tool 再填进来，名字 `mcp__<server>__<tool>`；Loop 看不见 MCP。工具用法写在 schema 描述里，不另设工具提示词段。

`read` / `bash` 回模型最多 2000 行、50 KiB。`edit` 的 `oldText` 必须恰好一次。普通工具错误回给模型；取消 Run 才终止。

## 6. Client

Client 是 app-server 的使用者，不是后台表面层。后台插件只登记数据与行为契约，不传 HTML、React 组件或任意 SVG。

```text
React          显示与局部交互
普通 TS        类型化 Client、连接、状态归并、订阅与重连
手写 TS 契约   方法名、参数、结果和事件类型
app-server     协议、校验、分发与连接生命周期
```

目标 Web 放在 `clients/web`，使用 React + TypeScript + Vite，不使用 Next.js。React 不拥有 Session、Run、Agent 或产品业务事实；它只保存服务端投影和路由、折叠、主题、草稿等界面状态。

运行画面由 Snapshot 与后续事件进入同一个 reducer。必须建立无空档的订阅边界；重连后重新取得历史、活跃状态、未落账草稿和待回答请求，再续订。无需重播断线期间每个文字 Delta，但不能漏耐久事实。增量、草稿和落账条目用同一个 Entry.ID 替换，不另加一条。慢 Client 不得阻塞 Runner。

各端平等：可查看、发送、Steer、停止和回答后台请求。关闭页面或断开连接不停止任务；明确 Stop 才取消。后台重启把未完成运行标记中断，不自动续跑。

Harness Client 首版迁移已有正式能力：项目/会话、聊天与图片、运行过程、模型/档位/Agent、命令与 Skill 候选、停止、分叉和设置。旧页面插槽与 demo 不属于迁移目标；真实新需求出现后再决定数据契约和 UI 组合方式。

分叉仍从已完成助手回答复制耐久历史和 SessionSettings，创建独立新会话，原会话不变。轨迹页仍只是同一份账本与运行数据的另一种投影，不修改 Runner。

旧 `surface/web`、`plugins/web`、Templ、HTMX、POST 与 SSE 只属于迁移期现状，完成迁移后整体删除，不维护双轨。具体 UI 规则见 `WEB_UI.md`。

## 7. 以后做也不改的边界

### 子会话委派：系统机制

Subagent：孩子自己一本 Session、自己的 Run；`subagents` 是管理委派关系与协作状态的整份服务，使用 Runner，不直接执行 Loop 或写对话账本。关系、逐轮结果位置与通知由它独立保存，子会话不进入普通聊天列表。重启只恢复记录，不自动执行。

```text
父 Loop → 普通 tools 登记处 → Subagents → 同一个 Runner → 子 Loop
                                ↑                       |
                                └─ 完成句柄 → 保存状态 ─┘
                                |
                                └─ Runner.Receive → 父账本 → 检查点 / 初始 History
```

**固定边界：** 第一版只允许一层委派；孩子不能继续派孩子。不设孩子数量或并发上限，不自动排队；不另建 jobs、运行器或子任务专用界面。工具只是入口，父子关系与协作规则由 Subagents 负责，实际执行和取消收尾由 Runner 负责。

**设置与隔离：** 孩子新建 Session，只接收委派说明，不复制父历史；不为每个孩子新建 Agent 设置。Agent ID、模型、思考档位分别继承父 Run 的配置快照，显式覆盖分别校验；覆盖模型后若继承档位不兼容则报错，不偷偷换档。工作区始终继承，父子共享文件，不自动建 worktree，也没有额外写入隔离。孩子每次启动仍读取自己 SessionSettings 和当前所选 Agent 设置；send 不修改设置。

委派工具插件向现有 `tools` 登记处填入 `subagent_options / spawn / send / list / wait / stop` 六个工具（均带 `subagent_` 前缀）。使用 Subagents，不另挂服务、不直接调用 Loop，也不保存自己的运行状态。调用身份来自程序提供的 SessionID / RunID / ToolCallID；模型只填写委派说明、可选设置和目标任务 ID。沿用普通 Tool 权限，安装不会自动给已有 Agent 勾选新工具。

options 直接查询现有 Agent 设置与模型清单，不维护第二份名单，不虚构 Agent 的“用途”字段。服务验证目标孩子归属；工具参数不能冒充父会话、父 Run 或工作区。工作区工具、平台工具和 MCP 等外部工具沿用同一登记处、权限检查、调用及结果落账，不因职责分类增加子登记处。

spawn 启动后马上返回；send 忙时 Steer、闲时在原有子会话开启新轮，发生可能已经接收的错误时不盲目重发。list 通过服务读取逐轮最终正文，任务 JSON 仍只存结果位置。

**耐久顺序：** 先保存关系，再创建子 Session 与设置，最后启动 Runner。TaskID 长期稳定；每轮单独保存递增轮次、RunID、状态、最终正文 EntryID 和通知。旧轮完整收尾并保存后才允许新轮，不能只看 RunHandle.Done 就覆盖旧结果。`subagents/tasks/<task-id>.json` 使用版本化 JSON 原子替换，写盘失败明确报错，不宣称可靠完成；最终正文只从该轮最后的最终助手回答读取，不能拿推理或工具前临时文字冒充结果。

Chat 用户停止经 `StopFamily` 取消父与全部孩子，父已闲置也有效；父正常回答结束不会停止孩子。Subagents 用内存中的停止代次与可信父 RunID 拦截停止前的在途 spawn / send，不建立协作级 Context。子 Run 的开始事件再校验一次，避免预检与真正启动之间漏停；停止不等待启动写盘锁。单独 stop 孩子保留记录，之后父明确 send 可开新轮；新父 Run 不会重新放行旧 Run 的在途指令。

wait 使用 `taskIDs` 等任一指定孩子当前或后续轮次的新完成结果，`seenNotificationIDs` 跳过已见通知；默认 60 秒、允许 0～60 秒。返回 `reason`、当前任务状态 `tasks` 和新完成通知 `notifications`（状态、轮次、通知 ID），不返回正文。等待不保持模型请求；用户 Steer 提前唤醒，取消 Context 结束等待，超时不停止孩子。当前任务进入新轮，也不覆盖此前等待的完成通知。

Subagents 保存完成状态、最终正文位置与稳定通知 ID 后才投递；失败、取消、中断明确标注。父运行中通过 Runner 在检查点接收；最终检查点已关闭则保留待投递，父闲置时不自动启动。下一次用户主动启动父会话时，现有 RunStarted 通知触发投递，首次模型请求前接收。投递确认写盘失败可重试，账本已存在消息 ID 就不再次注入正文。服务拥有通知重试后台与事件订阅，Close 解除订阅、取消并等待退出。

父账本保存平台工具结果及 `role=collaboration` 的带来源消息，不把任务状态当通用记录塞进账本。模型侧按带来源说明的普通输入处理，不冒充用户或系统指令。不新增 `subagent-*` 事件或前端 JS，Loop 里不分叉。停止后通知保留待投递，不唤醒父会话；已落账工具调用沿用 ReAct 取消收尾，补齐结果但不执行剩余工具。

**启动、关闭与恢复：** 固定 Runner → Subagents → 委派工具 → HarnessProduct，倒序关闭。Subagents 拥有孩子追踪、通知订阅与重试后台，关闭拒绝新请求，解除等待，取消孩子并等在途启动与后台退出，再关闭 Runner。服务生命周期 Context 只用于资源关闭，不承担父子业务关系。重启保留逐轮历史与待投递通知，把未完成轮次标记中断；不自动恢复执行，不自动唤醒父会话。

### 其他扩展边界

命令是平台能力的门，不是外部能力进来。新命令若需要新内部行为，先改 Runner / Session，插件保持很薄。

扩展开关（个人 Skill / 个人 MCP Server）若以后做：对所有 Agent 生效，不存进 Agent 或 SessionSettings；关 MCP 是不建立连接。现在没有开关 = 已发现的个人来源默认全开。项目来源不受个人开关控制。
