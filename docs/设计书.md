# 设计书

开工先读仓库根 `AGENTS.md` 和 `STATUS.md`；本篇写产品与架构方案。Cordis 对照见 `docs/reference/DSH项目心得.md`。

参考 DeepSeek Harness 和 pi，**不照抄**。Go 框架。静态编译。无热加载。无 AI 自改。前端：Go + templ + htmx。

本篇是项目的唯一总设计：既记录产品形状，也记录插件架构与运行边界。阶段文档记录各阶段的决断、实现和验收，不另起一套产品理念；`STATUS.md` 只记录当前进度。

## 1. 根是宿主，不是聊天

进程是一张服务表。聊天只是表上的一摊。

```
Host（宿主）                        桌子，不是插件
  ├─ web                 登记处 B      可选 Web 表面；登记产品、templ 组件和 HTTP 路由
  ├─ sessionPersistence  整份 A        最先挂。只负责账本字节。jsonl 或 sqlite，组装时选一个
  ├─ sessionSettings     整份 A        会话旁设置 For/Put。同一 persist 包实现，另一把键
  ├─ agentStore          整份 A        自建 Agent 设置的持久化读写。同一 persist 包实现，另一把键
  ├─ sessions            整份 A        对话账 Store。从 Persistence Load / Add
  ├─ llm                 整份 A        调 goai Provider；不自己适配线上协议
  ├─ machine             整份 A        提供者挂上之后才有。文件和进程在哪台机器
  ├─ tools               登记处 B      工具来填。Get machine，不自己当电脑
  ├─ events              登记处 B      跨插件的实时通知；不存储、不代替服务调用
  ├─ loops               登记处 B      react / graph / plan-act 等程序来填
  ├─ agents              整份 A        必装设置插件提供。用户 Agent 的实时配置
  ├─ Runner              整份 A        外壳；还没跑完的 Run 也在它手里
  ├─ 狼人杀              整份 A        验架构用，v1 不实现。可 Get Runner，棋盘不进账本
  └─ 多机器人讨论        整份 A        验架构用，v1 不实现。自己的房间；每个机器人一本 session
```

电影等纯 Web 产品是插件填入 `web.products` 的条目，不必在 Host 上另占服务键。只有确实要被其他插件调用时，产品才额外挂一份 A。

`RegisterService` / `Resolve`。定义者出契约，提供者装上，消费者 import 定义者。彼此不 import。

Loop 是怎么想的程序；Agent 是用户配置；正在跑的是 Runner 还没返回的 `Run`。

## 2. 宿主 Host

不是插件，是插件挂上去的地方。类型叫 `Host`，不叫 `App`（`App` 像整程序就是聊天）。

```go
type Host struct {
    services map[string]any
}

func (h *Host) RegisterService(name string, v any) error
func Resolve[T any](h *Host, name string) (T, error) // 没有或类型不对 → error
```

插件 `Start` 时往上挂；`Close` 倒序拆。没有这张表，后面谁都没处放。

`main` 里谁先 `Start` 谁先挂。persist 包 `Start` 时挂上 `sessionPersistence`、`sessionSettings` 和 `agentStore`；`sessions` 在它们后面；yaml 选出的 machine 提供者在 `tools` 前面；`agents` 设置插件在 `tools`、`loops`、`skills` 之后、Runner 之前。不要给 Host 加优先级，不要 inject 等待。

### 组装：配置选启不启动，顺序写在代码里

插件必须先编译进去。配置只决定这次 `Start` 哪些已经有的实现，不按包名热加载，不让用户改启动顺序。

```yaml
persist: jsonl      # 或 sqlite。A，包内选文件
machine: local      # 选哪个提供者插件。必装，不进 enable

enable:
  - web        # templ + htmx；GUI 是这套外面套 webview，不要再画一遍
  - tui        # bubbletea，可选
  - acp        # 协议桥，不是画面
```

```go
h := NewHost()
startKernel(h, cfg)          // 顺序写死
if cfg.On("movie") {
    movie.Start(h)
}
if cfg.On("werewolf") {
    werewolf.Start(h)
}
```

内核（Host、persist（两把键）、session、llm、tools、events、loops、Runner）每次都 Start，不出现在 `enable` 里。`agents` 由必装的设置插件提供，在 Runner 前 Start。machine 契约在 kernel，实现按 yaml 必装一个提供者，也不进 `enable`。`web` 启用时先挂上 Web 服务，需要页面的插件再往里登记。卸的是表面（web / tui / acp）和桌上可选的一摊。

| 配置能做 | 配置不能做 |
|---|---|
| web / tui / acp 上场或不上场 | 发明一份还没写的插件 |
| machine 选哪个实现；persist jsonl 或 sqlite | 两个同时挂；改 Start 顺序 |

「卸」= 这次不 `Start`（v1 改配置后重启）。代码还在二进制里。再装回来 = 写回 `enable`、再 Start。不要做成 DSH 的 `cordis.yml`：那是按包名拼插件树，顺序和清单都在 YAML 里。

新写一种机器或一种游戏，仍要编译。配置不能凭空变出一份没有的 Go 程序。另做一个产品（只看电影）= 另写一个 `cmd` 的 `main`，少 Start 几样，不是用户 YAML 把内核拆掉。

### 跨插件通知：events

`events` 是登记处（B）：插件登记「我想听什么」，发布者发出一条事件，`events` 当场通知已登记的听众。它不保存事件，不写账本，也不替代有返回值的服务调用。

```text
需要执行 / 要结果：Resolve 服务 → 调方法
只需通知 / 不要结果：events → Publish → 已登记的听众
```

事件的名字和数据形状由领域定义者声明；发布者、订阅者都 import 这个定义，不在各插件里临时手写字符串和 JSON。

```text
Loop → Runner → Append 成功 → events.Publish(RunEvent)
                                  ├─ web：转 SSE
                                  ├─ tui：刷新终端
                                  └─ 观测：记录指标
```

`RunEvent` 的唯一发布者是 Runner。Loop 只能把内部事件交给 Runner；Runner 转换成稳定的对外 `runner.RunEvent`。UI / TUI 只订阅，不能伪造运行事件。对外事件不直接包装或暴露 `loops.Event`，换 Loop 不能迫使表面跟着改。

`RunEvent` 覆盖一轮运行的全部过程：

```text
run-started
text-delta / reasoning-delta
tool-started / tool-finished
message
run-ended：success / cancelled / failed + error
```

`message` 是已经成功落账的完整消息；Delta 和工具状态只用于当前画面。开始与结束事件让各个表面可靠判断「发送 / 停止」状态和展示错误。`SessionID` 表示是谁在运行；事件只描述发生了什么，卡片画法不进事件契约。

## 3. sessionPersistence

整份服务（A）。只负责字节。jsonl 或 sqlite，组装时选一个。

最先挂。`sessions` 在它后面。

```go
type Persistence interface {
    Load(id string) (*Tree, error)
    Save(id string, tree *Tree) error
    List() ([]Meta, error)
    Add(id string, node Node) error
}
```

选 jsonl 或 sqlite 其中一份实现。`Start` 时挂 `sessionPersistence`、`sessionSettings` 和 `agentStore` 三把键。表上各永远一份，不要两套存储同时挂。

不认识 `Append` / `History` / `Branch`。不广播。不是喇叭。Session 去 **调用** 它，不是它去 **听** 账本。

热路径不写盘，指的是 **字级 Delta**（Durable=false 的蹦字），不是完整条目。

不要 DSH 那套 coordinator、flush 事件、投影、标题服务。会话标题是 Session 元数据，不另起服务。`Persistence` 接口不出现 SessionSettings。

同一 `Start` 再挂一把键 `sessionSettings`（另一份 A，另一个接口）。jsonl / sqlite 仍是这个包内部选文件，不是两个 enable 插件。

```go
type SessionSettingsStore interface {
    For(sessionID string) (SessionSettings, error)
    Put(sessionID string, s SessionSettings) error
}
```

`SessionSettings` 没有切片；For/Put 返回独立值。自建 Agent 的切片在 `agentStore` 读写时深拷贝，避免 UI 与正在跑的 `Run` 抢同一片切片。

## 4. Session

整份服务（A）。对话账。表上挂的是 Store。`Start` 时 `Resolve("sessionPersistence")`。

```go
func (s *Store) Create(id string) (*Session, error)
func (s *Store) Get(id string) (*Session, error)
func (s *Store) List() ([]SessionMeta, error)
func (s *Store) Rename(id string, title string) error

func (s *Session) Append(message Message) error
func (s *Session) History() []Message
func (s *Session) Branch(id string) error
```

`SessionMeta` 是独立于账本和 `SessionSettings` 的持久化元数据，v1 只有 `ID / Title / CreatedAt`。新建时标题为「新对话」；Session 服务在首条用户消息成功落账后自动命名，以后可由用户重命名。它不是消息，不进账本；也不影响运行，不塞进 `SessionSettings`。

只记人 / 模型 / 工具结果。模型那一行是一列有序块（`reasoning` / `text` / `tool-call`）；每条 Tool 消息只有一个 `tool-result` 块，保存调用 ID、工具名、交给模型的内容和错误标记。todo、审批、游戏棋盘，**放插件自己的结构体**。

`Append` = 写穿完整条目（jsonl 一行 / sqlite 一条）。字级 Delta 只走本轮事件流，不进 `Append`。进程崩了：已 Append 的还在，正在蹦、尚未 Append 的半截丢掉。

v1 不做摘要压缩。`History()` 沿当前分叉整段现算。预留：树上可挂一种摘要块；`History()` 碰到它就从摘要往下拼，摘要之上不发给模型。谁压、何时压，以后另写，不改 Host / Runner 形状。

形状学 pi：可以分叉。不是 DSH 那种只能往下接、什么都往里扔的流水账。

```
用户: 帮我改登录
  └─ 模型: 用方案 A
        ├─ 用户: 就用 A     ← 指针在这
        └─ 用户: 改用 B     ← 旧路还在，没删
```

只有一份。树在 Store 手里；磁盘是 Persistence 的事。不要两份长期分开养（pi：内存一列消息 + 文件一棵树，来回抄）。`History()` 现算，不是第二本活数组。

热路径（字一个个出来）不写盘。`Append` 已经写穿完整条目。回合结束不必再整树重写；`Persistence.Save` 留给换后端、迁移、补快照。jsonl 以追加行为准。

**屏幕不听账本。** 一句说完由 Runner `Append`。Session 是账，不是喇叭。

| 要干什么 | 听谁 |
|---|---|
| 现在这句正在往外蹦 | 这一轮 `Runner.Run` |
| 打开旧对话、画分叉、画轨迹 | 读 Session |

喇叭就这一个。标题、压缩、计数：听同一轮 Run。todo：屏幕在「工具结束」时去读它的服务。别每个插件各喊各的。

v1 不把本轮 System Prompt、时长或 token 另写进账本。轨迹页先使用已有 Session 与当前 RunEvent；以后确实需要运行元数据时再单独设计，不暗塞进 Message。

## 5. llm

`llm` 是 A 服务。`Plugin.Start` 读取本机 YAML、构造 Client，并挂到 Host 的 `"llm"` 键；Client 直接调用 goai，不再自己实现各家线上协议。

```text
llm.RunConfig{Model, ReasoningEffort}
              + Input{System, History, Tools}
                         |
                         v
                  llm.Client.Stream
                         |
                         v
                  goai LanguageModel.DoStream
                         |
                         v
                  <-chan provider.StreamChunk
```

React Loop 取完整历史和本轮提示词，调用它；Graph Loop 可以完全不碰。人仍只调用 `Runner.Run`。

### 两份数据

```text
kernel/llm/models.json
  版本控制的模型定义：Provider、远端模型 ID、思考档位对应的专有请求 JSON。

~/.harness/config.yaml
  本机部署配置：BaseURL、API key。启动时读一次，不进仓库。
```

`SessionSettings.Model` 是 `models.json` 的键；`SessionSettings.ReasoningEffort` 是该模型 `reasoning` map 的键。模型和思考档位是两个独立选择框；首次发送前两项都必须选好。`off` 是明确选择，空值只表示尚未选择；不存在的档位在请求前报错。

```json
"off":  { "thinking": { "type": "disabled" } }
"high": {
  "thinking": { "type": "enabled" },
  "reasoning_effort": "high"
}
```

这些 JSON 原样交给 goai 的 `ProviderOptions`。Provider 的消息、流、thinking、图片和工具协议由 goai 处理；我们不写 HTTP、SSE 或自己的协议转换。

### 一次调用

```text
1. 按 Model 找模型定义和 YAML Provider 配置
2. 每次调用新建对应 goai 模型实例
3. Session History → goai Message
4. DoStream(System, Messages, Tools, ProviderOptions)
5. React Loop 消费 text / reasoning / tool-call / finish / error 事件
```

goai 没有总构造器；只为实际启用的 Provider 写明确分支，例如 `deepseek.Chat(...)`。当前实现 DeepSeek；需要另一家时才加一分支，不建注册表。

Tool 消息的 `tool-result` 块转为 goai 的 `PartToolResult`；调用 ID保证它与前一条 assistant 工具调用配对。

## 6. machine

文件和进程在哪台机器上。

A 是表上挂好之后的形态，不是某个目录。

- `kernel/machine`：定义者。只放契约。自己不 `RegisterService`，所以它不是 A，也不是「只有一个插槽的 B」。
- `plugins/kernel/machine/local` 等：提供者。Start 时 `RegisterService("machine", 实现)`，表上这把键才变成 A。
- yaml 选启动哪一个。表上永远一份。不要做成单槽登记处再取一次。

Go 代码直接 `Resolve("machine")`。模型不会 Go，只能走 Tool；read / write / edit / bash 内部再调它。

```go
type Machine interface {
    ReadFile(path string) ([]byte, error)
    WriteFile(path string, data []byte) error
    Run(ctx context.Context, dir string, argv []string) (stdout, stderr []byte, err error)
}
```

`Run` 只执行 argv，不解释 shell 语法。bash Tool 收到模型给的命令字符串后，明确转成
`[]string{"bash", "-c", command}` 再调用 `Run`。管道、重定向、`&&` 和引号归 bash，
不塞进 Machine 契约。

```
kernel/machine/          契约
plugins/kernel/machine/local/   本机
plugins/kernel/machine/e2b/     E2B
plugins/kernel/machine/xxx/     以后的云沙箱：新插件 + cmd 名单多一行
```

不要拆成 `shell` + `fs` + `subprocess` + `e2b` 四把键。机器是一个主人；箱子寿命藏在那份实现里。工作区是 SessionSettings 里从哪个目录开始，不是另一种机器。不限制路径。

电影不碰它。

## 7. tools

登记处（B）。一条工具不是一份 Host 服务。

表上挂的是空名单。v1 默认四条，都来填槽，都走 machine：

| 名字 | 干什么 | 调 machine |
|---|---|---|
| read | 读文件 | ReadFile |
| write | 整文件覆盖写 | WriteFile |
| edit | 精确替换一段 | 先 ReadFile 再 WriteFile |
| bash | 跑命令 | Run |

没有 `Create` 出来的活 Tool。不做 grep / find / ls（bash 能做）。不做 powershell。spawn / wait / stop 是子任务，不是这四条，见 §12。

Tool 作者只写参数结构体和 tag；不手写 JSON Schema，也不接原始 JSON。

```go
type WriteArgs struct {
    Path    string `json:"path" jsonschema:"minLength=1"`
    Content string `json:"content"`
}

tools.New("write", "整文件覆盖写", func(ctx context.Context, call tools.Call, args WriteArgs) (tools.Result, error) {
    // args 已通过 Schema 校验
})
```

登记时，由结构体和 tag 自动生成 JSON Schema，并编译校验器。模型回来后：

```text
Function Call 参数 JSON → tools 校验 → 转为 WriteArgs → 调具体 Tool
```

`tools` 只管登记、授权和校验；不取 machine。每个具体 Tool 插件在 Start 时取
`machine`，再 `Register` 自己。

`Register` 是填槽。`Call` 是使用。React Loop 调登记处，不自己翻 map。登记处按名找；名字不在 `call.Allow` 里直接错误。不要只靠给模型的 schema 名单当权限。

问模型那一轮：

```
Agent.Tools     →  Get("tools") 现取 schema  →  塞进 llm.Input.Tools
agents.Prepare(AgentID, Workspace)             →  最终 System Prompt
模型要调工具   →  名字必须在 inv.ToolNames 里
               →  tools.Call(ctx, Call{Workspace: ..., Allow: ..., Name: ..., Arguments: ...})
               →  Schema 校验后，具体 Tool 调 machine；路径相对 Workspace
               →  产出工具起止事件（屏幕）
               →  产出工具结果事件（Runner 先 Append）
```

某个 Agent 可以名单更窄，也可以一个都没有。Graph Loop 可以完全不碰这张表。

不要为 bash 再挂一个 `shell` 键。bash 就是一条 Tool，跑命令走 machine。

MCP 是服务提供者，不给 LLM 直接调用：MCP 服务把远端能力包装成普通 Tool，再填 `tools`。包装名统一为 `mcp_<server>_<tool>`，例如 `mcp_github_create_issue`；Agent 只选择 Tool，前端可按此前缀显示 MCP 来源。MCP 是否启用属于进程配置。

工具的基本用法写在参数 tag 生成的 `Schema` 描述里。不要另设工具提示词段，也不要把 schema 写进 System Prompt。

`read` 和 `bash` 回模型前最多 2000 行、50 KiB：read 留开头，bash 留结尾并标明截断。
`edit` 的 `oldText` 必须恰好出现一次；零次或多次都不改文件。普通工具错误回给模型；取消 Run 才终止。

## 8. System Prompt

没有 `prompts` 登记处。System Prompt 是 Agent 设置的一部分，默认 Agent 的文本由代码内置；自建 Agent 可编辑完整文本。

`agents.Prepare(AgentID, Workspace)` 每轮现取 Agent 和最新 Skills 摘要，拼出最终文本：

```text
Agent.SystemPrompt

## Available Skills
- <name>: <summary>

## Workspace
<workspace>
```

未选 Skill 时省略 Skills 段。Agent 只保存 Skill 名，不复制摘要；默认 Agent 使用当前全部已登记的 Skill，因此新增 Skill 后下一次 Run 自动出现。任何未来插件若要影响 System Prompt，必须成为 Agent 的明确配置，不可暗中插入一段。

---

## 9. Loop

一种程序怎么想。`loops` 是登记处（B），登记可复用、并发安全的程序；活着的 Run 只在 `Runner.live`。

```text
"react"     → 默认 LLM + Tool loop
"graph"     → 工作流
"plan-act"  → 以后可加的另一种范式
```

换默认范式：替换 `"react"` 的程序。想让用户选择：登记新 Loop，再由 Agent 设置选它。不要预建通用 Loop 插槽。

Loop 插件在 `Start` 时自己 Resolve 所需服务；例如 React 取得 `llm`、`tools` 后填入 `loops`。`Run` 不再接触 Host，也不取 `Session`、`SessionSettings`、`Runner`。Runner 只传本轮数据与 `Emit` / `Checkpoint`。

## 10. Agent 设置与 SessionSettings

**Agent** 是用户创建、实时修改的配置，由必装插件提供 `agents` 服务：

```text
Agent：Kind / SystemPrompt / Tools / Skills
SessionSettings：AgentID / Model / ReasoningEffort / Workspace
```

`agents` 插件 Resolve `loops`、`tools`、`skills`；保存 Agent 时校验 Loop、工具和 Skill 名。它保存 Tool / Skill 名，不复制摘要；每次读取时取最新 Skills 摘要。它不是可选 `enable` 插件，因为 Runner 每轮都依赖它。

默认 Agent 表示使用当前全部已启用 Tool 和 Skill；自建 Agent 从已有名单里选子集。服务决定系统里有什么，Agent 决定本轮能用什么。

SessionSettings 是会话旁路配置，不进账本。创建会话时选 Agent，并写入 AgentID；前端改模型、思考档位、工作区都 `sessionSettings.Put`。Agent 设置和 SessionSettings 都是实时配置，但 Runner 每轮只读取一次；改动影响下一次 Run，不打断当前 Run。

Runner 每轮调用 `agents.Prepare`，再组合结果和 SessionSettings，得到本轮只读配置：

```text
Agent.Kind / Tools
最终 SystemPrompt
SessionSettings.Model / ReasoningEffort / Workspace
```

### Invocation

Loop 拿到的本轮输入：

```text
History      从账本提取，已包含本次用户输入
SystemPrompt Runner 已拼好的本轮系统提示词
LLMConfig    Model / ReasoningEffort
ToolNames    Agent 本轮允许的工具名
Workspace    本轮工作区
Checkpoint   一步结束时检查并接收已入账的 Steer
```

`ctx` 是 `Loop.Run` 参数。Loop 不拿账本服务，不 Append，不知道 SSE；React 使用启动时取得的 `llm`、`tools` 和本轮 Invocation，持续产出事件。

## 11. Runner

整份服务（A）。一场调用的运行时外壳。一般只装一个；`live` 只保存尚未结束的 Run。

```text
1. 取 Session、SessionSettings；调用 `agents.Prepare` 取 Agent、最新 Skills 摘要和最终 System Prompt
2. 组合本轮配置，按 Agent.Kind 找 Loop
3. 初始用户输入先 Append，再从账本取 History；把本轮数据交给 Loop
4. 调 Loop.Run，顺序消费事件：完整消息先 Append，再发布给 UI
5. 管理取消、FollowUp、Steer、Stop；Spawn / Wait 属于后续子任务功能
```

账本只有 Runner 能写；UI 只订阅 Runner 的本轮事件流。v1 一轮只服务一个实时 UI；后来打开页面读 Session。

### FollowUp / Steer

```text
FollowUp  当前 Run 已结束；同一本 Session 再开一次 Run
Steer     当前 Run 未结束；暂存到 Runner.live 的队列
```

Loop 在每个检查点——一次 LLM 回复及其全部 Tool 都处理完——向 Runner 请求继续。Runner 先确认前面耐久事件已入账，再按顺序 Append 队列里的 Steer，最后把已入账的新消息交回 Loop。最终检查点发现队列为空时，会原子关闭 Steer 入口；之后的新消息明确失败，不会成功后丢失。Checkpoint 只用于内部协作，不进账本、不发 UI。

这样所有用户消息都只由 Runner 写账；不会把 `tool_call` 和 Tool 结果拆开。每种 Loop 都必须到检查点处理 Steer；不支持就不能登记。打断正在流的半句是 `Stop`，不是 Steer。

UI 可在 Run 尚未结束时让用户选择 FollowUp 或 Steer；默认选择属于 UI 插件的全局设置，不属于 SessionSettings。当前 Runner 已实现 Run / FollowUp / Steer / Stop；Spawn / Wait 尚未实现。

## 12. 异步子任务

平台功能。不是某种 Agent 自己会的本事。

不要的：工具里面把子 Agent 跑完再返回。  
要的：工具只下令，马上返回。孩子在宿主里自己跑。

```
宿主 / Runner
  父 Run(session 父)     还在转
  子 Run(session 子)     另开一条

三个工具（挂在 tools 上，Get Runner；不是默认四条，v1 后做）：
  spawn  再调一次 Runner.Spawn，立刻给 id
  wait   Runner.Wait
  stop   Runner.Stop
```

分叉处是再进一次 **Runner**。Loop 里不分叉。子任务有自己的 session；按子 SessionSettings 的 AgentID 取 Agent 设置，再按其 Kind 选 Loop。

**spawn 工具负责造孩子，再调 `Runner.Spawn`。** `Spawn` 吃的是已经存在的 sessionID。

```
spawn 工具 Call：
  1. 深度 = 父链长度。超过 Runner 策略 → 错误，不建账
  2. 新建子 session（Store）
  3. Put 子 SessionSettings：默认拷父 SessionSettings；工具参数可换 AgentID、模型、档位、工作区
  4. Runner.Spawn(子 sessionID, 话)  →  进 live，立刻返回子 id
```

孩子的寿命不能绑在 spawn 这次工具的 `ctx` 上。工具返回了孩子还得在；只有 `stop` 才杀掉。

父账本只记 spawn / wait / stop 的工具结果。子账本是子自己的。屏幕要看子任务：听子那一轮 `Run`。

`spawn` 工具结果要持久返回 `ChildSessionID`，子 Session 元数据记录父子关系。Agent 卡片只是 `spawn` 工具的专用画法：它从父账本得到子 ID，父页面原有的一条 SSE 连接同时接收子孙 Session 的事件，再按子 ID 更新对应卡片。不为每张卡片新开 SSE 连接。子 Agent 的思考、文字、工具和结束全部复用普通 `RunEvent`，不增加 `subagent-*` 事件。

```text
事件       描述发生了什么
卡片       决定画成什么样
SessionID  决定是谁发生的
```

不抄 DSH 那一套 subagent 插槽（六个后端、jobs、Activation）。v1：进程内 goroutine、三个工具、深度限制是 Runner 的策略。

## 13. Web 表面

`surface/web` 是可选插件，同时提供页面和 HTTP 路由两种登记口。契约就在
`surface/web/types.go`；不再设 `kernel/http` 和 `kernel/pages`。

```go
// 契约。Web 插件提供的扩展入口。
type Service interface {
	RegisterProduct(product Product) error
	RegisterRoute(pattern string, handler http.Handler) error
	Products() []Product
}
```

`Products()` 返回排序后的产品副本，产品 Handler 用它组合通用 templ 页面壳；不能直接修改登记处状态。

Web `Start` 时创建产品和路由登记处，以 `web` 挂上 Host，登记 HTMX、静态资源和
通用外壳路由，然后启动 `net/http.Server`。**Web 不登记 Chat，也不认识 Runner、
Session 或对话页面。** 后续产品插件 Resolve `web` 后登记产品和 Handler。全部插件
启动成功后才打开浏览器。
填充者 import `surface/web` 这个定义者；Web 不 import 任何填充者。

Web 产品和页面插槽填充物按契约所有者放在 `plugins/web`：Chat 产品位于
`plugins/web/chat`，其 composer / dock / sidepanel 填充物继续收在 Chat 子树；
Web 公共设置填充物位于 `plugins/web/settings`。内核运行链的具体实现统一位于
`plugins/kernel`。目录表达依赖方向，不代表动态加载或新的 Host 层级。

```go
webService, err := host.Resolve[web.Service](h, "web")
err = webService.RegisterProduct(MovieProduct{})
err = webService.RegisterRoute("GET /movie", MoviePage{})
```

Handler 用结构体实现 `ServeHTTP`，不写闭包。路由只在启动时登记，不做单条注销。
`Close` 停止 Server，断开 SSE，取消 Web 启动的任务，并等待它们退出。不启用 Web，
就没有页面、HTTP 登记处或端口监听。

请求 POST；字往外蹦 SSE。都走这份登记处。v1 不用 WebSocket。普通发话调
`Runner.Start`（由 Runner 在后台执行 `Run`），明确插话调 `Runner.Steer`；HTTP 不先看 live 自动分支。

同一进程（CLI）：Run 调一下听的人。完了。浏览器过不去进程，才需要管子：

```
点按钮 / 发话       → POST
字蹦出来 / 工具在跑 → SSE（还是 HTTP，只下行）
```

SSE 是浏览器先发起一条长时保持的 GET，Web 再在这条 HTTP 连接上持续写事件。两段监听不要混在一起：

```text
Chat 监听 Runner：Go events.Subscribe[runner.RunEvent]
浏览器监听 Chat 路由：HTMX SSE 扩展
```

Chat `Start` 时订阅一次 `RunEvent`，按 `SessionID` 转给对应的 SSE 连接；`Close` 时注销。Chat 把 SSE Handler 登记到 Web 路由。浏览器用 HTMX SSE 扩展的 `hx-ext="sse"` / `sse-connect` 建连和自动重连，不自己创建 `EventSource`。

聊天消息区统一走 JSON + 一份 JS/TS `paint()`：Chat 把 `RunEvent` 转成命名 JSON SSE；少量 JavaScript 在
`htmx:sseBeforeMessage` 里阻止默认 HTML swap、解析 JSON，更新消息、思考、工具和运行状态，再调用 `paint()`。
耐久 `message` 事件已经表达完整消息已落账；`run-ended` 结束当前助手卡并显示消息动作，不再 GET HTML，也不换皮。刷新或重新打开会话时，Web 的 History HTTP 接口返回耐久消息 JSON，仍交给同一个 `paint()`；Run 结束后 History 与 SSE 的最终状态一致，Run 进行中则由 SSE 补充尚未落账的半截。

Go 的 Session 仍是事实来源，浏览器 `messages` 只是它的画面投影；JS 不写账本。`templ` + HTMX 负责页面壳、侧栏、设置、产品切换和普通表单，不负责聊天消息气泡。

```html
<div hx-ext="sse"
     sse-connect="/chat/{id}/events">
  <div sse-swap="run" hidden></div>
</div>
```

```text
Delta / Tool RunEvent → Web JSON SSE → HTMX SSE 负责连接 → JS 更新 messages → paint()
message / run-ended   → JS 固定耐久消息、结束当前 Run → 同一个 paint()
刷新 / 重开会话        → History HTTP JSON → 同一个 paint()
```

一张会话页只开一条长期 SSE：本轮 `run-ended` 只把「停止」改回「发送」，下一轮继续复用连接；关闭页面或切换会话才断开。Chat 的 Go 监听回调只把事件放进按 Session 分组的内存队列，必须立即返回；不准等浏览器。某个 SSE 客户端太慢、队列满了，就断开该连接，不能卡住 Runner。重连时重新读 History JSON；正在生成但尚未落账的半截 Delta 允许丢失。

DSH 用只下行 WebSocket，而且是账本转给浏览器。我们只学「请求和通知分开」，不学它的账本投影和 WebSocket。

HTTP 请求的 Context 只管理这次 POST 或 SSE 连接，不能直接作为 Runner 任务的 Context。关闭页面只断开 SSE；任务继续运行。显式调用 `Runner.Stop` 或 `Runner.Close` 才取消任务；Chat `Close` 只注销事件订阅并关闭自己的 SSE 连接，Runner `Close` 负责等待所有 Run 退出。

## 14. 产品与页面插槽

产品和页面插槽是两个层级：产品决定进入哪一摊；页面插槽只扩展某个产品内部。

```text
Host
└─ web 服务
   ├─ routes 登记处 B
   ├─ products 登记处 B
   │  ├─ Chat 产品插件填入 chat
   │  ├─ Movie 产品插件填入 movie
   │  └─ Werewolf 产品插件填入 werewolf
   └─ 公共设置插槽
```

### 产品登记处

产品条目只登记用户入口所需的事实：`ID`、名称、图标、顺序、`BasePath` 和左侧产品导航。产品内部可以有多个页面，各 HTTP 路由返回 templ 片段，HTMX 整体替换固定的 `main`。

插件是启动代码；产品是插件填进 `products` 的用户入口。Chat、电影、狼人杀都是产品插件；工具插件通常不登记产品。

### Web 页面外壳

```text
Web
├─ 左侧栏：产品入口 + 当前产品导航
└─ main：随当前产品页面整体替换
```

点击产品入口只请求对应路由，不刷新整个网页，并同步更新 URL；直接访问 URL 也能打开对应页面。`main` 是整页出口，不是页面插槽，浏览器不再维护第二棵插件树。

设置页的插件配置统一放在「插件」一级栏目下，再二级选择具体插件；其他一级栏目待设计。

### Chat 产品

`plugins/web/chat` 是静态编译的产品插件。它 Resolve 自己真正需要的
`web`、`sessions`、`sessionSettings`、`runner` 等服务，然后登记 Chat 产品和路由。
Web 不认识 Runner、Session 或 Chat 页面；电影等产品可以只使用 Web，零依赖聊天。

Chat 的项目、会话和输入区属于产品固定功能：

```text
项目            按 Workspace 分组的 Session，不是独立数据
新建项目        原生目录选择 → 创建 Session → 写入 Workspace
模型 / 思考档位 两个独立选择框，首次发送前都必须选好
主按钮          空闲显示「发送」；运行时显示「停止」
```

项目侧栏从 `sessions.List()` 和 `sessionSettings.For(id)` 现算，不新增 projects 服务。目录选择器是 Chat 内部的平台适配；当前只做电脑端。

### 页面插槽形状

四种形状只按真实需要使用：

| 形状 | 含义 | Harness 用法 |
|---|---|---|
| `single` | 一个占用者，整体替换 | 当前产品导航 |
| `list` | 多个条目按顺序追加 | 消息动作、Dock、输入动作、设置栏目 |
| `keyed` | 按类型名选择画法 | 右侧面板类型 |
| `chain` | 按状态决定谁接管 | 未来多个输入区接管者出现时再实现 |

Chat 专属插槽由 Chat 自己提供的登记处管理，不各自在 Host 上占服务键；`settings.section` 是 Web 公共插槽。

### Chat 页面固定区域

```text
顶部：对话 | 轨迹              → Chat 固定 Tab，不是插槽
消息卡片下方：message.actions   → 复制、分叉、插件动作
输入框上方：dock                → Todo、Goal、子任务等持续状态
输入工具栏：composer.actions    → 附件、图片、语音等输入动作
右侧：sidepanel                 → file、browser、editor、chat 等面板类型
```

- `message.actions` 是 `list`。当前已实现登记处和内置 `copy`；助手复制只取同一 Run 段最后一条有正文的 assistant 消息，忽略 reasoning、工具和相邻 Steer 段。不内置点赞、点踩。
- `dock` 是可独立折叠的持续状态列表，状态不写入 Session。Chat 提供登记处与折叠外壳；填充插件提供 `templ.Component`，业务状态变化后发布 `DockChanged`。Chat 用同一条 SSE 发送 `dock-{id}` HTML，HTMX 只替换该条目内部内容；首次连接和重连都发送当前内容。
- `composer.actions` 只改变输入产生方式，不改变固定的发送、停止、模型和思考档位。
- 审批不走弹层；未来由同一输入区切换为审批框，多个接管者出现后再抽 `chain`。
- `sidepanel` 是 `keyed` 插槽。Chat 固定画 Tab 栏、`+`、关闭和宽度；插件登记面板类型并提供内容。工具调用仍在消息卡片中，工具可以触发打开面板。

### 右侧面板的状态边界

右侧面板只属于 Chat 页面：

```text
Chat 固定外壳       → Tab 栏、+、关闭、宽度
面板插件            → 登记类型、画内容
浏览器临时状态      → Tabs、当前 Tab、开关、宽度
Session             → 完全不保存面板状态
```

相同 `(Type, InstanceKey)` 只聚焦已有 Tab，不同身份才新开。当前只用 `demo` 验证登记边界；文件、浏览器、编辑器面板属于后续实现。v1 刷新或切换会话不恢复面板状态，未来确有需要时再使用浏览器本地存储。面板内部按钮由面板自己渲染，不另设 `sidepanel.actions`。

### 当前实现与后续

| 插槽 | 当前状态 |
|---|---|
| `message.actions` | 已实现登记处与 `copy`；分叉和第三方动作后续实现 |
| `sidepanel` | 已实现 keyed 登记处与独立 demo；真实面板后续实现 |
| `dock` | 已实现 `list` 登记处、Templ 内容与同 SSE HTML 更新；动态 demo 只在自动化测试安装 |
| `composer.actions` | 已实现 `list` 登记处与独立 demo；组件由填充插件使用 Templ / 原生 HTML / HTMX 绘制 |
| `settings.section` | 已实现 Web 公共登记处、Master-Detail 页面与独立 demo |

页面插槽只给 Web / webview 的 templ 外壳；TUI 自己画。游戏页面自己更新自己的状态，不把状态倒进聊天账本。

### 对话 / 轨迹

同一份对话的两种固定画法，不改 Runner：

```text
对话页     气泡：可见文字、折叠思考、工具卡
轨迹页     时间线：SYSTEM → USER → ASSISTANT → 工具，加上时长、轮次
```

正在发生听这一轮 Runner 事件流；打开旧内容读 Session。v1 先做对话气泡，轨迹页属于阶段 5。

## 15. 多端适配

内核一份。表面按端 `enable`。洞不是端。

```
内核     Runner / Session / llm / tools / machine
喇叭     这一轮 Run 的事件流

表面（配置开关）
  web    templ + htmx，自己提供 HTTP；SSE 把本轮事件送过进程
  tui    bubbletea，同进程直接听本轮事件
  acp    协议桥：编辑器 ↔ Runner.Run，不画聊天页
```

画面不同就要各自画。**Web 和 GUI（webview）是同一套 templ**，只是窗口不一样，不要画两遍。开 webview = 还是 `enable: web`，外面套窗口（或 web 插件配 `open: browser | webview`）。TUI 另画。ACP 不画；所有 ACP 编辑器共用这一份插件。

不是四种前端四种插件体系。DSH 是同一套 base 换外壳（web-app / headless / ACP 桥）；浏览器里再跑一棵 React/Cordis——不抄。

## 18. 明确不抄

| 不抄 | 学 |
|---|---|
| DSH 账本当产品仓库 + 喇叭 | 账本只记对话 |
| DSH 听账本投影轨迹页 | 对话 / 轨迹是同一数据的两种画法 |
| DSH 持久化听 session/event / flush | Session 自己 Save；持久化只是字节 |
| DSH 转圈焊进活 Agent；Chat.Followup / Inbox | 闲着再 `Run`；跑着 `Steer`。没有 Followup 方法 |
| DSH 提示词代收 schema + `{{var}}` + 拼装瀑布 | System Prompt 属于 Agent；schema 走 `tools` |
| DSH 七种 StreamChunk + assembler 服务 | 有序块：Index + Kind + Delta |
| DSH / 自造多份 Provider 协议代码 | 一份 `llm`，直接使用 goai 的 Provider 实现 |
| DSH `shell`+`fs`+`subprocess`+`e2b` 四把键 | 一份 `machine`；换沙箱 = 换提供者插件，不改契约 |
