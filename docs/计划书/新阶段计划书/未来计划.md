# 未来计划

## 对话轨迹

轨迹的唯一数据来源是 session 账本。它不直接展示原始 JSONL，而是把账本事件整理成轮次、消息、模型请求、工具调用、结果、耗时和状态。

```text
账本 → 对话投影 → 简洁聊天页
     └→ 轨迹投影 → 详细调试页
```

轨迹只读取账本，不修改账本，也不向 loop 增加专用数据。等聊天页稳定后，再作为独立视图实现。

## Web UI 的扩展原则

- Web UI 继续使用 Go `templ` + HTMX + Tailwind；暂不做原生 GUI。
- 网页壳子只负责通用布局和少量明确位置：设置页、聊天卡片、聊天操作、独立页面。
- 新功能需要页面内容时，写自己的网页伙伴插件：它领取自己的领域能力和 `uiweb`，再向对应位置登记内容；不要每加一个功能就硬改网页壳子。
- 先出现第二个真实需求，再增加新的位置；不预造通用前端插件系统。

## 下一阶段：插件扩展基础设施

当前的基础盘已经解决了“插件如何被组装、如何领取能力、如何运行 Agent”。下一阶段要解决的是：

```text
一个插件如何自带配置、命令、Agent 上下文和界面
```

这部分参考 `reference/deepseek-harness` 的 `commands`、`settings`、`credentials` 和 `ui-slots`，但只吸收适合本项目的边界，不照搬它的动态系统。

### 1. Commands：人类命令基础设施

Slash Command 不是 Tool，也不是 Web 路由。Tool 是模型调用，Command 是人直接调用。

```text
commands Service
  ├─ Register
  ├─ List / Find
  ├─ Execute
  └─ 命令生命周期与取消
```

- `commands` 只负责登记、发现、解析和分发，不知道 Web、templ、HTMX 或具体业务。
- 能力插件注册自己的命令，并调用自己拥有的 Service；核心能力、领域能力和第三方能力使用同一套注册方式。
- Web UI 只负责显示 `/` 菜单、参数提示和转发执行结果，不写 `if /movie` 之类的业务分支。
- 命令默认不进入模型、不消耗 token、不经过 Tool Pipeline；命令确实需要模型时，由命令插件显式调用 Agent。
- 未知命令不静默降级为普通消息。
- 所有 Slash Command 统一使用 `/` 激活；命令前缀表示调用语义，不表示能力来自核心还是插件。
- 核心命令和插件命令通过命令元数据、菜单分组等方式区分，不另造 `$` 激活体系；`$` 暂不承担命令激活职责。

### 2. Settings 与 Credentials：插件自包含配置

现在的配置主要集中在 `compose.Config`，模型凭据也跟供应商配置耦合。未来插件应能够声明自己的配置空间和凭据需求：

```text
插件
  ├─ 声明 settings namespace
  ├─ 读取自己的配置
  └─ 通过 CredentialRef 获取密钥
```

- `settings` 负责配置，不负责业务状态。
- `credentials` 负责密钥，不允许 UI 或普通业务代码直接暴露明文。
- 插件自描述所需的 Settings、Credentials 和校验规则；`compose` 只负责组装，不了解每个插件的具体字段。
- API Key、Token 等密钥只传给真正需要它的适配器，不能进入 UI、日志、Session 或普通配置读取接口。
- 模型插件只声明“需要什么凭据”，不拥有全局配置结构。
- 这会让新增插件不必持续修改中心配置文件。

### 3. Prompt / Context：Agent 上下文贡献

当前系统提示词主要来自 Preset。未来增加独立的 Prompt Service：插件只登记材料，不直接拼接最终 Prompt。

插槽按寿命分三类，不按插件分：

```text
Prompt Service
  ├─ RegisterSection    长期规则
  ├─ RegisterMemory     会话备忘
  ├─ RegisterSituation  当前处境
  └─ Assemble           每个 step 组装
```

- `Section`：每次请求都带，不进聊天账本。人设、框架身份、Plan 开着时的政策都放这里。Plan 是带开关的长期规则，不是临时往聊天里倒一段字。
- `Memory`：进账本；没变不记账，变了追加一份带来源的整份替换。AGENTS.md、Skill 目录、重要通知用 `kind` 区分，不另开注册表。账本事件不是 `user/message`。Skill 正文走 Tool，不进插槽。
- `Situation`：每个 step 现算（时间、目录、沙箱状态）。不在聊天里堆积；审计走 `request/snapshot`。
- 人话和工具结果不是插槽。
- loop 是唯一组装者，也是唯一往账本写上下文的人。
- 发给模型时稳定内容在前、易变内容在历史之后：这是摆放，不是第四类插槽。
- 工具怎么调用只走 `tools` JSON。跨调用习惯以后需要，再让那个工具填 `Section`；现在不预做。
- 第一版只做这三类和 `Assemble`。不发明通用临时 Prompt 垃圾桶，也不提前做变量、作用域覆盖和抑制。

### 4. UI Contribution：界面扩展插槽

后端插件提供或领取服务。前端网页伙伴往已经挖好的洞里填界面。壳子只负责有洞，不知道电影。

```text
电影服务插件     只管片源和播放状态     不认识网页
电影网页伙伴     领取电影服务 + uiweb  用 templ 画播放器，占洞
Web 壳子         按洞渲染              不写 if 电影
```

- 抄竞品的「壳子挖洞、功能占洞、加功能不改壳子」。不抄它的 React 组件热加载和客户端打包。
- 网页伙伴交出的是真正的 templ 界面，不是一份让壳子猜着画的说明书。只交描述会把上限卡死：壳子会画什么，插件才能有什么。
- 领域插件不碰 templ / HTMX；认识网页的只有它的网页伙伴。
- `/` 命令不需要每个命令自己做 UI。命令插座列出菜单，一个命令界面去画。
- 扩展上限 = 有没有这个洞，以及占洞的人能不能自己画。洞不存在，必须先声明；洞已在，加功能不改壳子。
- 不预造完整 Slot 引擎。第二个真实界面需求出现时，再挖那一个洞。候选位置包括：侧栏脚、设置页、聊天卡片、右侧面板、浮层、独立整页。


### 5. Subagent 与 Jobs：Agent 生态基础设施

`subagents` 是“派助手中心”：它是平台能力，不是 Tool，也不直接属于 `agents` 或 `loop`。

```text
subagents 平台
├─ 派出、查看、等待、取消子 Agent
├─ 管理父子身份、权限和生命周期
└─ 按名字选择具体执行后端 Provider
```

子 Agent 不是一个神秘的新 Runner，而是独立的 Session：`agents` 创建它，`loop` 正常驱动它。

```text
父 Conversation
  └─ subagents.Start(可信父身份, 任务)
       └─ Provider 创建 child Session
            └─ agents + loop 驱动孩子工作
```

`Start()` 只等孩子成功创建、接到初始任务，立刻返回 `childID` / `ChildRun`；不等孩子完成。启动时同时选定“完成后怎样交给父亲”：唤醒父 Agent，或只给人显示完成状态。

```text
childID / ChildRun
├─ Get / List       看状态
├─ Wait             等结果
└─ Cancel           停止孩子
```

插件关系固定如下：

```text
subagents 插件
├─ 使用 "agents"：创建、打开运行中的 Conversation
├─ 使用 "sessions"：登记并保存子 Agent 的账本资料
├─ 提供 "subagents"：派助手中心
└─ 创建 "subagent-providers" 插槽：登记 Provider

subagent-inprocess 插件
└─ 填充 "subagent-providers"：注册 in-process Provider

tool-subagent 插件
├─ 使用 "subagents"
└─ 填充 "tools"：注册给 LLM 用的 subagent 工具
```

因此 Tool 只是遥控器，不是核心：

```text
LLM      → tool-subagent → subagents
Web / 命令 ─────────────────→ subagents
```

每个子 Agent 管自己的完整账本；父账本只记“派出了谁”、平台的完成通知和必要的交回结果，不复制孩子的全部历史。

```text
所有 Session Header 都使用同一套字段
├─ ParentSessionID  直接父会话；主会话为空
├─ Origin           user / subagent
└─ DelegationDepth  当前委派深度

子账本的 subagent/descriptor 事件
└─ Provider、模式、标签等 subagents 专属资料
```

- 父子关系是通用、永久事实，放在 Header；Provider、模式、标签是 subagents 的细节，放 `subagent/descriptor` 事件。
- 不能只凭猜到的 `childID` 控制孩子；只有可信的直接父 Agent 才能查看、等待或取消自己的孩子。
- 创建顺序必须是：校验 → 预留身份 → 创建 → 发布 → 接受初始任务；任一步失败都完整回滚，不留下半成品。
- 默认不复制父会话历史；父亲只交付任务与明确选中的必要材料。将来若做 `fork`，必须作为显式模式，而不是隐式继承。
- 子 Agent 完成时，`subagents` 平台必须在父账本记录 `subagent-settled`：这是平台陈述“孩子已完成”，不是伪装成孩子说的话。
- 若启动策略是“唤醒父 Agent”，平台把这条完成通知投进父 inbox 的 `next-turn`，父 Agent 随后开新 Turn；若是“仅通知”，只给 Web / 命令显示，不额外消耗父模型。
- 完成通知 `settled` 与未来的主动汇报 `report` 必须分开：`settled` 是平台自动的最终状态；`report` 是孩子工作中主动选择交付的内容，未来可投递到 `next-step`。

第一版只做最小但不埋雷的能力：

```text
V1
├─ 一个 in-process Provider
├─ 独立子 Session + 独立账本
├─ 异步 ChildRun：状态、等待、取消
├─ 父子关系持久化与创建回滚
├─ 自动 settled 完成通知
├─ 选择“唤醒父 Agent”或“仅通知”
└─ 限制：深度 1、每个父会话最多 2 个孩子
```

第一版不做：可继续子 Agent、Followup、Report、冷恢复、父历史 fork、外部 Codex/ACP/Claude Provider、嵌套子树 UI。

后续演进的边界：

```text
V2  可继续子 Agent：同一 child Session 可再次接任务
V3  Followup / 主动 Report / 父子树 UI
V4  Codex、ACP、Claude 等外部 Provider
```

`jobs` 仍是独立的平台能力：它管理下载、命令、批处理等泛后台工作。一次性子 Agent 将来可以被 `jobs` 展示或包装；可继续子 Agent 不能被硬塞成 Job。

### 6. Projection / Query：账本的一本多读与轨迹图

同一个 Session 只有一份事实账本；“对话”和“轨迹”只是读取它的两种视图，不创建第二份聊天记录或 Trace 账本。

```text
Session Event Ledger
├─ 对话页：看说了什么
├─ 轨迹页：看怎样完成
├─ Token / 成本页：看花了什么
└─ 未来搜索页：找发生过什么
```

轨迹图是账本的只读投影：先读取当前 Session 的历史事件和实时新增事件，再统一组装成 `TrajectorySnapshot`，最后由 UI 显示时间条、列表和详情。UI 组件不自行解析 JSONL，也不修改账本。

```text
历史读取 + 实时新增事件
          ↓
TrajectorySnapshot
├─ 时间条：Input / Model / Tools
├─ 列表：Turn / Step / Tool
└─ 详情：输入、输出、原始数据、指标
```

轨迹必须忠实保留所有**模型或运行时实际可观测到**的工作事实：

```text
一次 Turn / Step
├─ 用户输入与进入时间
├─ System Prompt、模型、思考档位、工具目录的请求快照
├─ Thinking：服务商实际返回时，保留其内容与流式片段
├─ 普通输出：流式片段与最终定稿
├─ Tool Call：名称、参数、开始、结果、状态、耗时
├─ Step / Turn：开始、首 token、结束、取消或失败原因
└─ 用量：输入、缓存读写、输出、Thinking Token、成本（服务商提供时）
```

- 不猜测、伪造或补写模型没有返回的 Thinking、Token、缓存或时间指标；没有就明确显示“不可用”。
- 当前账本已记录 Turn、Step、请求快照、Tool 生命周期、事件时间、最终 Thinking 和用量。未来需要把 Thinking 流、普通输出流、首 token 时间和各类用量拆成可独立追踪的事件，才能完整实时画出轨迹。
- 轨迹页首次只加载最新历史窗口；向上滚动再加载更早窗口。实时事件按 `seq` 增量追加、去重；出现断档才重新同步，不能每个 token 整页重算。
- 搜索先只查当前已加载的轨迹窗口；跨 Session 搜索属于后续 `Query Service`，不是轨迹图 V1 的前置条件。

实现顺序保持克制：

```text
V1  Session Events → TrajectorySnapshot → 对话 / 轨迹切换
V2  历史分页、实时增量、窗口内搜索、完整指标事件
V3  Token / 成本等独立投影，跨 Session Query
```

不预造万能 Projection 注册表、持久化轨迹缓存或全文搜索；第二种真实投影出现后，再抽共同能力。

## 后续基础设施顺序

```text
第一阶段：Settings + Credentials + Commands
第二阶段：Prompt / Context
第三阶段：UI Contribution
第四阶段：Subagent Runtime + Jobs
第五阶段：Session Projection / Query + Spill + Telemetry
第六阶段：Remote Adapter + Attachment + 持久 Terminal
```

已有能力不重复建设：`core.App`、事件总线、作用域、`agents.Conversation`、Session 账本、loop 恢复和 Context 取消已经是基础设施的一部分。工具流水线已有前置检查 / 问人 / 守卫；审批和沙箱是以后填这个插槽的插件，不另起一层统一权限基础设施。

暂不建设：

- 通用 Storage Service：已有 Project Store、Preset Store 和 Journal，不能用万能 KV 抹平领域语义。
- Storage Domain 大一统：如果未来需要切换 JSON、SQLite 或其他后端，只抽象存储后端，不抹平 Project、Preset、Session 的领域语义。
- 通用 Cache Service：先有明确的 Projection / Query 需求，再决定缓存策略。
- 动态插件加载、热更新和 HMR：本项目坚持静态编译插件。
- 完整 RPC / Remote Gateway：本地进程内边界尚未遇到真实瓶颈。
- Schedule：定时任务属于后续领域插件，不是当前 Agent 地基。

## 已确定的 Web 规则

- 左栏是 `Project → Session`；Agent 模式不是主页第一层。
- 新会话先是空草稿，首次发送才创建 Session 并锁定模式版本。
- Agent 模式只保存提示词和工具白名单；模型从全部已安装模型中独立选择，变更写入账本。
- 添加项目使用本机目录选择框，目录名自动成为项目名。

## TUI

TUI 暂停。旧原型在 `reference/terminal-v1`，不参与编译；等 Web 产品流程稳定后再决定保留或移除。
