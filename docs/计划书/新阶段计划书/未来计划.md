# 未来计划

## 对话轨迹

轨迹的唯一数据来源是 session 账本。它不直接展示原始 JSONL，而是把账本事件整理成轮次、消息、模型请求、工具调用、结果、耗时和状态。

```text
账本 → 对话投影 → 简洁聊天页
     └→ 轨迹投影 → 详细调试页
```

轨迹只读取账本，不修改账本，也不向 loop 增加专用数据。等聊天页稳定后，再作为独立视图实现。

## Web UI 的扩展原则

- Web UI 继续使用 Go `templ` + HTMX + Tailwind；暂不做原生 GUI。
- 网页壳子只负责通用布局和少量明确位置：设置页、聊天卡片、聊天操作、独立页面。
- 新功能需要页面内容时，写自己的网页伙伴插件：它领取自己的领域能力和 `uiweb`，再向对应位置登记内容；不要每加一个功能就硬改网页壳子。
- 先出现第二个真实需求，再增加新的位置；不预造通用前端插件系统。

## 下一阶段：插件扩展基础设施

当前的基础盘已经解决了“插件如何被组装、如何领取能力、如何运行 Agent”。下一阶段要解决的是：

```text
一个插件如何自带配置、命令、Agent 上下文和界面
```

这部分参考 `reference/deepseek-harness` 的 `commands`、`settings`、`credentials` 和 `ui-slots`，但只吸收适合本项目的边界，不照搬它的动态系统。

### 1. Commands：人类命令基础设施

Slash Command 不是 Tool，也不是 Web 路由。Tool 是模型调用，Command 是人直接调用。

```text
commands Service
  ├─ Register
  ├─ List / Find
  ├─ Execute
  └─ 命令生命周期与取消
```

- `commands` 只负责登记、发现、解析和分发，不知道 Web、templ、HTMX 或具体业务。
- 能力插件注册自己的命令，并调用自己拥有的 Service；核心能力、领域能力和第三方能力使用同一套注册方式。
- Web UI 只负责显示 `/` 菜单、参数提示和转发执行结果，不写 `if /movie` 之类的业务分支。
- 命令默认不进入模型、不消耗 token、不经过 Tool Pipeline；命令确实需要模型时，由命令插件显式调用 Agent。
- 未知命令不静默降级为普通消息。
- 所有 Slash Command 统一使用 `/` 激活；命令前缀表示调用语义，不表示能力来自核心还是插件。
- 核心命令和插件命令通过命令元数据、菜单分组等方式区分，不另造 `$` 激活体系；`$` 暂不承担命令激活职责。

### 2. Settings 与 Credentials：插件自包含配置

现在的配置主要集中在 `compose.Config`，模型凭据也跟供应商配置耦合。未来插件应能够声明自己的配置空间和凭据需求：

```text
插件
  ├─ 声明 settings namespace
  ├─ 读取自己的配置
  └─ 通过 CredentialRef 获取密钥
```

- `settings` 负责配置，不负责业务状态。
- `credentials` 负责密钥，不允许 UI 或普通业务代码直接暴露明文。
- 插件自描述所需的 Settings、Credentials 和校验规则；`compose` 只负责组装，不了解每个插件的具体字段。
- API Key、Token 等密钥只传给真正需要它的适配器，不能进入 UI、日志、Session 或普通配置读取接口。
- 模型插件只声明“需要什么凭据”，不拥有全局配置结构。
- 这会让新增插件不必持续修改中心配置文件。

### 3. Prompt / Context：Agent 上下文贡献

当前系统提示词主要来自 Preset。未来增加独立的 Prompt Service：插件只登记材料，不直接拼接最终 Prompt。

插槽按寿命分三类，不按插件分：

```text
Prompt Service
  ├─ RegisterSection    长期规则
  ├─ RegisterMemory     会话备忘
  ├─ RegisterSituation  当前处境
  └─ Assemble           每个 step 组装
```

- `Section`：每次请求都带，不进聊天账本。人设、框架身份、Plan 开着时的政策都放这里。Plan 是带开关的长期规则，不是临时往聊天里倒一段字。
- `Memory`：进账本；没变不记账，变了追加一份带来源的整份替换。AGENTS.md、Skill 目录、重要通知用 `kind` 区分，不另开注册表。账本事件不是 `user/message`。Skill 正文走 Tool，不进插槽。
- `Situation`：每个 step 现算（时间、目录、沙箱状态）。不在聊天里堆积；审计走 `request/snapshot`。
- 人话和工具结果不是插槽。
- loop 是唯一组装者，也是唯一往账本写上下文的人。
- 发给模型时稳定内容在前、易变内容在历史之后：这是摆放，不是第四类插槽。
- 工具怎么调用只走 `tools` JSON。跨调用习惯以后需要，再让那个工具填 `Section`；现在不预做。
- 第一版只做这三类和 `Assemble`。不发明通用临时 Prompt 垃圾桶，也不提前做变量、作用域覆盖和抑制。

### 4. UI Contribution：界面扩展插槽

后端插件提供或领取服务。前端网页伙伴往已经挖好的洞里填界面。壳子只负责有洞，不知道电影。

```text
电影服务插件     只管片源和播放状态     不认识网页
电影网页伙伴     领取电影服务 + uiweb  用 templ 画播放器，占洞
Web 壳子         按洞渲染              不写 if 电影
```

- 抄竞品的「壳子挖洞、功能占洞、加功能不改壳子」。不抄它的 React 组件热加载和客户端打包。
- 网页伙伴交出的是真正的 templ 界面，不是一份让壳子猜着画的说明书。只交描述会把上限卡死：壳子会画什么，插件才能有什么。
- 领域插件不碰 templ / HTMX；认识网页的只有它的网页伙伴。
- `/` 命令不需要每个命令自己做 UI。命令插座列出菜单，一个命令界面去画。
- 扩展上限 = 有没有这个洞，以及占洞的人能不能自己画。洞不存在，必须先声明；洞已在，加功能不改壳子。
- 不预造完整 Slot 引擎。第二个真实界面需求出现时，再挖那一个洞。候选位置包括：侧栏脚、设置页、聊天卡片、右侧面板、浮层、独立整页。

### 5. Subagent 与 Jobs：Agent 生态基础设施

未来如果要真正支持多个 Agent 协作，不能让业务插件直接创建某个具体 Runner。需要一个面向平台的运行时：

```text
Subagent Runtime
  ├─ Provider 登记
  ├─ 创建 / 列出 / 关闭子 Agent
  └─ 将子 Agent 作为可取消、可观察的任务运行
```

长时间运行的下载、批处理、子 Agent 和后台工具，也不应全部挤进 Conversation。`jobs` 负责统一管理：

```text
创建 → 观察 → 等待 → 取消 → 获取结果
```

它们属于 Agent 平台基础设施，不属于某个具体业务插件。

### 6. Projection / Query：让账本服务多种视图

轨迹页、调试页、搜索和统计不应该各自从 JSONL 重新猜历史。未来增加投影和查询层：

```text
Session Events
  ├─ 对话 Projection
  ├─ 轨迹 Projection
  ├─ Token / 成本 Projection
  └─ Query Service
```

Projection 仍然只从账本计算，不改变账本事实。历史变大后，再增加投影快照或检查点；不提前做万能缓存。

### 7. 平台边界：Remote、Spill 与 Diagnostics

当前 Web 和运行时在同一进程内，直接调用是合理的。未来出现 CLI、TUI、移动端或第三方客户端时，再抽出：

```text
业务 Service → API / Remote → Web、CLI、TUI、SDK
```

工具输出过大时，可增加 `Spill Store`，把大内容放到外部存储，只把引用放进上下文和账本，避免撑爆 Token 和 Session。

同时增加可选的 Runtime Diagnostics / Invariants，让插件声明并检查：

```text
必需能力存在
资源是否正确释放
插件是否重复注册
```

这些能力都应保持可替换，不把某一种数据库、RPC 或监控系统写死进核心。

## 后续基础设施顺序

```text
第一阶段：Settings + Credentials + Commands
第二阶段：Prompt / Context
第三阶段：UI Contribution
第四阶段：Subagent Runtime + Jobs
第五阶段：Session Projection / Query + Spill + Telemetry
第六阶段：Remote Adapter + Attachment + 持久 Terminal
```

已有能力不重复建设：`core.App`、事件总线、作用域、`agents.Conversation`、Session 账本、loop 恢复和 Context 取消已经是基础设施的一部分。工具流水线已有前置检查 / 问人 / 守卫；审批和沙箱是以后填这个插槽的插件，不另起一层统一权限基础设施。

暂不建设：

- 通用 Storage Service：已有 Project Store、Preset Store 和 Journal，不能用万能 KV 抹平领域语义。
- Storage Domain 大一统：如果未来需要切换 JSON、SQLite 或其他后端，只抽象存储后端，不抹平 Project、Preset、Session 的领域语义。
- 通用 Cache Service：先有明确的 Projection / Query 需求，再决定缓存策略。
- 动态插件加载、热更新和 HMR：本项目坚持静态编译插件。
- 完整 RPC / Remote Gateway：本地进程内边界尚未遇到真实瓶颈。
- Schedule：定时任务属于后续领域插件，不是当前 Agent 地基。

## 已确定的 Web 规则

- 左栏是 `Project → Session`；Agent 模式不是主页第一层。
- 新会话先是空草稿，首次发送才创建 Session 并锁定模式版本。
- Agent 模式只保存提示词和工具白名单；模型从全部已安装模型中独立选择，变更写入账本。
- 添加项目使用本机目录选择框，目录名自动成为项目名。

## TUI

TUI 暂停。旧原型在 `reference/terminal-v1`，不参与编译；等 Web 产品流程稳定后再决定保留或移除。



# 代码组织更新计划

## 插件是安装单位，能力是使用单位

插件不默认注册一个包揽全部职责的巨型 Service。`Plugin.Start` 负责组装，可以按真实边界注册零个、一个或多个小能力，也可以只填充其他插件提供的插槽：

```text
Plugin.Start(app)
├─ RegisterService("capability-a", ...)
├─ RegisterService("capability-b", ...)
├─ OtherSlot.Register(...)
└─ 订阅事件 / 登记清理
```

- `App` 中登记的是能力名，不是插件名；一个插件可以提供多个能力。
- 使用者只领取自己需要的最小能力，不依赖整个插件或巨型组合结构。
- 对外提供的能力接口与供其他插件填充的插槽接口分开设计、分开命名、按能力分文件；不堆进笼统的 `interfaces.go`。
- 插件内部可以用私有组合器组装共享依赖；能力对象共享私有 `state`，不要回指整个组合器。
- 按职责边界拆分，不按代码行数或字段数量机械拆分；单一职责的 `llm.Service`、`tools.Registry` 不因结构体较大而强拆。

`agents` 是第一处需要按此原则整理的模块：

```text
agents.Plugin
├─ Conversations   给 Web UI 等消费者使用的会话能力
├─ RunnerSlot      给 loop 等执行插件填充的 Runner 插槽
└─ state           sessions、opening、依赖和锁等私有共享状态
```
